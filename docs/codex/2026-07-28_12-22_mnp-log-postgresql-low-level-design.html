MNP log data flow
Proposed design

Raw evidence stays still. The current view can change.

MNP log entries are inserted once and never updated. Stitching changes only the smaller transaction and assignment tables. After 60 days, verified Parquet becomes the historical store.

The central rule: regrouping may replace the current interpretation, but it never edits or deletes the raw log evidence.
01 / Mental model

Four responsibilities, kept separate.

Original evidence

log_entries

Immutable server output. Think of these as paper receipts that are never rewritten.

Current interpretation

log_transactions

The transaction folders that currently make sense from the available evidence.

Current membership

log_entry_assignments

Removable labels saying which folder contains each receipt and in what order.

Historical evidence

Verified Parquet

Checksummed daily history after the PostgreSQL hot period has ended.

04 / Late entry

A corrected view without changing evidence.

Before E4 arrives

E1  REQUEST   → T1 sequence 0
E2  MI CALL   → T1 sequence 1
E3  RESPONSE  → T1 sequence 2
→

After late E4 arrives

E1  REQUEST   → T1 sequence 0
E2  MI CALL   → T1 sequence 1
E4  ERROR     → T1 sequence 2
E3  RESPONSE  → T1 sequence 3
E1, E2, and E3 are never updated. E4 is inserted once. Only T1 and its assignment labels are atomically replaced.
