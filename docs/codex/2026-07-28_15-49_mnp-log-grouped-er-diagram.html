01 / Grouped ER

Every table has one clear job.

Showing the complete proposed MNP data model.
Group 1

Collection and provenance

Answers where the data came from and what ingestion attempt produced it.

log_ingestion_batches

One SSH poll, upload, watcher operation, replay, or backfill.

log_source_objects

One exact file or file segment with offset, fingerprint, and checksum.

produces raw evidence ↓
Group 2

Immutable evidence

Answers what the MNP server actually wrote.

log_entries

The source of truth. Insert once, never update during stitching.

is interpreted by stitching ↓
Group 3

Stitching and current view

Answers what work ran and how entries are currently grouped.

log_stitch_requests

A durable ticket saying which time range needs work.

log_stitch_runs

One execution, algorithm version, counts, fingerprints, and result.

log_transactions

The current business transaction summaries users query.

log_entry_assignments

The current bridge from each entry to a transaction and sequence.

is exported and verified after 60 days ↓
Group 4

Archive verification

Answers whether older data was safely exported before hot partitions are removed.

log_archive_manifests

Row counts, schema, fingerprints, checksums, URI, and verification status.

Verified Parquet

Historical entries, transaction snapshots, and assignment snapshots.

02 / Comparison

What moves, what is added, and why.

Existing implementationProposed MNP design
jobs

Shared by document processing and MNP ingestion. Deletion can cascade into raw logs.

→
log_ingestion_batches

MNP-specific attempt, counts, time range, idempotency, and restricted deletion.

log_entries

Stores raw evidence plus mutable transaction_id and seq.

→
immutable log_entries + log_entry_assignments

Evidence stays unchanged. Current membership moves to a smaller bridge table.

source_file text

Names the source but does not identify an exact version, fingerprint, or byte range.

→
log_source_objects

Records exact file, offset range, size, fingerprint, and checksum.

log_regroup_pending

Durable dirty range with retry and dead-letter information.

→
log_stitch_requests

Keeps the good dirty-range design and adds explicit status, worker lease, expiry, and recovery.

log_regroup_runs

Aggregate finalize status, counts, error, and JSON result.

→
log_stitch_runs

Per-execution windows, algorithm version, code revision, counts, and fingerprints.

No archive manifest table

There is no normalized proof that Parquet is safe before hot data is removed.

→
log_archive_manifests

Stores row counts, schema, URI, timestamps, source fingerprint, checksum, and verification.

03 / Problems solved

Each structural change has a specific reason.

Current behavior or gapWhy it is a problemProposed solution
Stage 2 updates raw entriesWrite amplification, dead tuples, index churn, and vacuum pressureReplace current assignments separately
Shared document and MNP jobMixed lifecycle and accidental cascade-deletion riskMNP-specific ingestion batch with restricted deletion
Filename-only provenanceCannot prove exact source version and byte rangeNormalized source-object fingerprint and offset
Large unpartitioned log tablesGrowing indexes and expensive retentionDaily UTC partitions with 60-day hot boundary
Pending work has no worker leaseHarder crash recovery and horizontal scalingLeased stitch requests with expiry
Limited stitch lineageHarder to explain which algorithm created the current viewVersioned stitch runs and fingerprints
No verified archive ledgerUnsafe to remove PostgreSQL data without export proofVerified archive manifests before partition removal

05 / Key relationships

Remember only these three paths first.

1

Where evidence came from

log_ingestion_batches ↓ log_source_objects ↓ log_entries

An ingestion attempt reads a source file or segment and produces immutable entries.

2

What users currently see

log_transactions ↓ log_entry_assignments ↓ log_entries

The assignment bridge finds the immutable entries belonging to a current transaction.

3

Why the current view exists

log_stitch_requests ↓ log_stitch_runs ↓ transactions + assignments

The work ticket and execution record explain which algorithm produced the current view.

06 / Bridge table

The assignment table connects the view to the evidence.

log_transactions

Folder T1 is the current summary of one business transaction.

→

log_entry_assignments

E1 belongs to T1 at sequence 0. E2 belongs to T1 at sequence 1.

→

log_entries

E1 and E2 contain the immutable server messages and parsed fields.
