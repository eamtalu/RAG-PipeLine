Log data architecture · central reference

How log files become transactions — today, and at 100× scale

One reference for both halves: how the two-stage pipeline works today (fetch → stitch, by time not by file, with backfill and catch-up), and the target design that lets the same data be ingested at scale, served fast, and mined by ML — each on storage suited to its job.

1 · How it works today

Two decoupled stages: fetch, then stitch

Fetch pulls files and drops their lines into a pool of timestamped log_entries — each file also flags the time-range it touched. Stitch later groups those entries into log_transactions by time, not by file, so a request in one rotated file and its response in the next reassemble automatically.

All of a poll's files are ingested first (each just drops entries and marks its dirty range); the stitch then runs once per customer over those ranges, cluster by cluster (below). So the order files arrive never affects grouping.

One poll → one stitch → N clusters

The stitch does not take one giant min(start)…max(end) window. It sorts the dirty ranges and walks them: a range joins the current cluster only if it starts within 30 min (= 2 × the 15-min pad) of that cluster's running end — otherwise it opens a new cluster.

Poll → stitch → run → window · keep this in your head

1 POLL  — fetch every file (all sources), ingest ALL of them first
  └─ 1 STITCH  — finalize_pending, once per customer   (N = #clusters, by the 30-min-gap rule)
       ├─ RUN / CLUSTER #1   span = hi − lo  · data-driven · NO max
       │     └─ sliced into ≤6h sub-windows → each padded ±15m → COMMIT
       ├─ RUN / CLUSTER #2   (own transaction — a failure here is isolated)
       └─ …  (one branch per cluster)
run == cluster
Same thing in the code (runs = _coalesce_pending(...)). 1 stitch = N runs.
run span
hi − lo of the cluster — data-driven, no maximum. Minutes in steady state; hours/days after downtime.
the only cap
6 h caps the sub-window a run is sliced into — never the run itself. A 14 h run → 3 commits.

When a cluster keeps failing · retry, then dead-letter

A failed cluster stays open and retries on later polls — but not forever. Each failed stitch bumps a counter; at log_regroup_max_attempts (default 3) the window is ABANDONED and parked with a CRITICAL alert, so a poison window (malformed row, or a dead disk sector under it) can't burn the 120 s timeout every poll and starve healthy clusters.

isolation
only the poison window is parked — every other cluster keeps stitching.
visibility
GET /logs/regroup/status reports abandoned_windows; non-zero ⇒ investigate (usually the disk).
recover
fix the cause, then POST /logs/regroup/reset-abandoned re-arms it.
2 · The three timing numbers

What actually sizes a rebuild

hi − lodata-driven

The run / cluster width = how much contiguous log-time piled up since the last stitch. Not a setting. Seconds-to-minutes in steady state; only catch-up (downtime, a big backfill file) makes it larger.

6 hourscap

A ceiling: never rebuild more than this in one bite — bigger backlogs are chopped into ≤6 h windows. log_regroup_max_window_seconds. Rarely hit.

±15 minsafety pad

Every rebuilt window is widened 15 min each side so a transaction is never cut at the edge. log_regroup_pad = the seal window. This is the overlap tax when a run is split.

3 · Backfill & catch-up

A late/old file lands correctly in the past

  • ◦Fetch ≠ stitch. Files only drop timestamped entries and flag a dirty range.
  • ◦Stitch by time, not by file. A window reads every unassigned entry in a time range, ordered by timestamp — blind to which file delivered it.
  • ◦Clusters, not one giant window. The 30-min-gap rule splits dirty ranges into N clusters, each padded / ≤6h-split / committed on its own — a poison cluster fails alone, dead-lettered after 3 attempts.
  • ◦Order-independent & idempotent. Deterministic uuid5 ids mean re-running a window rebuilds identical transactions.
  • ◦Backfill is lossless. A late/old file marks its own old window dirty, forcing a delete-and-rebuild of exactly that slice.
Resume after downtime

The SSH poller re-reads with a bounded, forward-only resume and a circuit breaker (auto-disable after ~10 min of failure) so a return-from-outage can't flood the pipeline; entry_hash dedup makes every re-read correct. The backlog then drains cluster-by-cluster, each isolated and dead-lettered.

⚠ single rotational HDD — ~55 ms writes · already failing (bad sectors)
The self-inflicted wound

Stitch updates log_entries to stamp transaction_id/seq — and re-stamps the unsealed tail every poll. Indexed columns ⇒ ~10 updates per insert, 0% HOT, ~91% dead rows, a 40 GB heap, and a VACUUM/DELETE that can't run on a disk with bad sectors. The window model above is sound; the place it writes is the problem.

5 · The target design

Four layers, each on storage that fits its job

The medallion pattern: raw → refined-and-served → archived → ML-ready, so heavy readers never touch the busy writer. Crucially, the whole stitch/window model above is unchanged — only where it writes moves (Section 6).

Ingest / raw Serve / hot Archive / cold ML / predictions

Layer 1 — Ingest

Bronze · append-only
  • log_entries becomes INSERT-only — never updated.
  • The grouping result moves to a tiny side table log_entry_assignment.
  • Partitioned by month; retention = DROP PARTITION.
In plain terms
Stop rewriting the giant table. Write once, never edit — almost no bloat, far fewer disk writes, trivial cleanup. The outage's root cause goes away.

Layer 2 — Serve the feed

Silver · ~90 days hot
  • log_transactions partitioned by month, indexed for the feed.
  • Only ~90 days stay hot; older months detach to the archive.
  • Feed & alerts read only the small recent partitions.
In plain terms
Queries look at just the months they need, so the feed stays fast as data grows 100×.

Layer 3 — Archive & analytics

Cold · Parquet + DuckDB
  • Aged-out months export to compressed Parquet (~5–10× smaller), then the PG partition is dropped.
  • DuckDB (embedded) runs full-scan queries over Parquet.
In plain terms
History lives in cheap columnar files that ML can scan hard — never touching the live DB.

Layer 4 — Machine learning

Gold · features → predictions
  • Batch jobs build features; models train offline.
  • Results land in a small transaction_predictions table the feed joins cheaply.
  • Anomaly · forecast · tagging (tagging reuses the pgvector/Qdrant embeddings).
In plain terms
The slow ML math happens off to the side; the app only reads a tidy table of precomputed predictions.

7 · How the window model maps onto the new design

Everything in Sections 1–3 is preserved — only the write target moves

Today · stitch writes the raw table

A window's “delete + rebuild” UPDATEs transaction_id/seq on log_entries, and freeing the tail cascades → NULL on those rows.

tail re-stamped ~180× before sealing
every write hits the 40 GB table

New · stitch writes the assignment table

A window's rebuild deletes + inserts rows in the small log_entry_assignment; log_entries is never touched.

churn moves to a tiny, partitioned table
raw table stays append-only
Clustering · 30-min gap · 6h split
Unchanged — operates on timestamps in finalize_pending, untouched by the change.
±15-min pad = retention lag
The seal window bounds transaction span, so drop the entries partition 15 min after the transactions partition — no live txn can reference dropped data.
Deterministic ids
Unchanged (anchored on entry_hash) — a rebuild reproduces identical transactions and identical assignment rows.
Backfill / catch-up
Same lossless behaviour — and now the full-rebuild path reads the immutable raw table instead of rewriting it twice.
Dead-letter · advisory lock
Unchanged — per-window commit + failure isolation + 3-attempt dead-letter is exactly preserved.
“Needs grouping” signal
Was transaction_id IS NULL; becomes a window-scoped NOT EXISTS (assignment) anti-join — the one detail that must be reworked, not renamed.
The linchpin to test

Partitioning requires the UNIQUE(customer_code, entry_hash) dedup constraint to include the partition key. It survives as a partition-local unique because entry_hash includes the ms timestamp, so a duplicate always routes to the same monthly partition. This must be verified explicitly — it is the guarantee behind every resume/rotation/backfill scenario above.

8 · Edge cases & scale

What the code review forced into the design

Timestamp-less entries
Can't be range-partitioned → a monitored DEFAULT partition; only a full regroup places them.
Month-boundary transactions
Span ≤ the 15-min seal window → retention lag of 15 min is provably sufficient.
Late data past retention
Its hot partition may be dropped → route to an archive-append path; only drop a month after retention + a back-fill grace.
Archive/drop atomicity
Export → verify count+checksum → only then DROP PARTITION. Never drop before verified.
Per-customer id scan in _persist
Loads all txn ids for the customer — O(all) at 100×; scope it to the window/partition.
regroup_all memory
Loads all entries per customer; backfill must run per-month, resumable.
Bounded partition count
Partition by month only; don't sub-partition by tenant by default (avoids months×tenants explosion).
Deletion contracts
Server-delete keeps entries (no FK to source); customer purge removes assignment via the Job cascade, atomically.
Feed 2-query consistency
Deterministic ids keep the transaction→assignment→entry join stable across a mid-read rebuild.
Orphan guard
Explicit same-txn assignment delete + a periodic check for assignment rows with no transaction.

Full detail, with code references, in docs/data-architecture-scale-ml.md §7.

9 · Rollout

Phased — each step ships on its own

  1. Append-only entries
    Add log_entry_assignment; stitch writes it instead of updating log_entries; rework detection to the window-scoped anti-join. Removes the outage's root cause.
  2. Partition both tables by month
    Resolve the partition-local unique; add partition pre-creation + a monitored DEFAULT partition.
  3. 90-day retention + Parquet archive
    Verified export → DROP PARTITION with the 15-min lag; late-data policy.
  4. ML layer
    Feature build + transaction_predictions + a first model (anomaly/error), then forecasting and tagging.
  5. Hardware
    SSD/NVMe (the prerequisite for real 100×); an optional second node becomes the archive/ML host.
Approach 2 · recorded for review

One flat read model — serve the feed from transaction_view, not a join

Everything above (call it Approach 1) serves the feed by joining log_transactions ⋈ log_entry_assignment ⋈ log_entries, so the click-through detail depends on log_entries. Approach 2 adds a single denormalized read model that pre-resolves the whole transaction — header filters and the full request/response detail — so the feed and detail are served from one flat table with no join, and log_entries can be deleted independently. Validated as a CQRS materialized read model (best practice). Recorded here for later review; no code changed.

Approach 1 · join-served

Feed + detail render by joining the three tables and fetching each transaction's entries. The detail depends on log_entries being present.

read: join + per-txn fetch + sort
log_entries: required by the read path
storage: one copy (raw)

Approach 2 · flat read model

Feed + detail served from transaction_view (one row per txn, full resolved detail in JSONB). No join; log_entries never read by the feed.

read: single-row scan, no join
log_entries: prunable independently
storage: + resolved copy (until entries pruned)

steps holds the complete §6 detail as structured JSON — request line + dims, every MI call's inputs/outcome, SQL, errors, and the verbose-only INFO steps, plus the request/response body — so the click-through detail renders byte-identically even after log_entries is pruned.

Primary serving path
Feed list + single-transaction detail both read transaction_view directly — no join, no per-txn entry fetch, no Python sort.
Maintained by the stitch, not a crawler
regroup_window re-projects only the window it rebuilt, atomically with the txn write; no periodic full scan.
Augments, not replaces
The three write/derive tables stay (source of truth, debug agent, stitch). transaction_view is the read side only.
Independent log_entries pruning
Because the feed never reads log_entries, raw entries can be dropped on their own short horizon with zero feed impact.
Durable system-of-record
Once entries are pruned, transaction_view is the only record of those periods → back it up / replicate; sealed = final.
Feeds ML, doesn't serve it
Its resolved fields source the offline feature build; ML full-scans stay on the columnar archive.

Safe-to-prune interlock (the “done” marker)

Because the projection is written atomically with the transaction, a sealed transaction is already materialized — so sealed ⇒ done. For defense-in-depth keep a per-month materialized_through watermark and a pruned_through marker; the prune job enforces pruned_through ≤ materialized_through, so it can never delete entries for a window the read model hasn't captured.

Trade-offs to weigh at review

Extra storage (resolved detail duplicated until entries are pruned) + a re-project write per window rebuild; the projection can lag/desync (mitigated by atomic per-window writes + deterministic ids); and once entries are pruned, a period can no longer be re-stitched or repaired. Endorsed for a read-heavy feed + independent entry pruning; skippable if Approach 1's join is already fast enough.
