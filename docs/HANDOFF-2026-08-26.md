### What it is and where it stands

The head lane (chunks 72-76, sections 18s-18v in `docs/analytics-ml-architecture/final_architecture.md`, deep dive in Part I section 11.5) is the fast path that processes only new lines against parked state (`log_open_stream` + per-tenant `log_stitch_checkpoint`), instead of re-reading a padded window every tick.
It has been running in SHADOW since 2026-08-28: for every eligible window it builds a plan, the rebuild lane executes as the authority, and the two are compared per entry.
Three live divergences were found and fixed the same day (18t stale parked streams, 18s comparison artifact, 18v state wipe by overlapping windows + per-server stream key).
Since the last fix (commit a540fbe, deployed 2026-08-28 ~14:12 BST) the shadow is clean.
The code: `app/services/mnp_log_ingestion/pipeline/head_lane.py`; the wiring: `finalize_pending` in `derive_transactions.py`; the tests: `test_head_lane_chunk72.py`, `test_head_lane_shadow_chunk73.py`, `test_head_lane_seed_chunk74.py`, `test_head_lane_fallback_logging_chunk75.py`, `test_stream_state_scope_chunk76.py`.

### The daily check (2 minutes, on the server)

```
ssh amin@192.168.0.142
journalctl -u fastapirag-worker --since "-24 hours" --no-pager \
  | grep -oE "shadow AGREED|shadow DIVERGED|fell back to the rebuild lane for .* - [a-z_]+$" \
  | sed -E "s/.* - /decline: /" | sort | uniq -c
```

How to read it:

- `shadow AGREED` - the head lane matched the authority on that window. The number you want to grow.
- `shadow DIVERGED` - STOP; do not promote. Pull the full lines (`journalctl ... | grep "shadow DIVERGED"`): each names the mismatched entries and transactions. Hand them to Claude - every divergence so far was diagnosable from that evidence alone.
- `decline: <reason>` - the head lane refused the window and the rebuild handled it; safe, not a failure. Expected reasons: `behind_checkpoint` (common), `no_rows`, `clock_went_backwards`, `parked_closed`, `parked_unreadable`, `parked_requestless`, `parked_lone_request`, `anonymous_open`, `parked_merge`, `id_clash`. A reason suddenly dominating is worth a question but blocks nothing.

### The decision rule - SUPERSEDED 2026-09-01 (section 18ab)

The owner's standing decision after measurement: the REBUILD LANE stays the production path; the shadow stays ON as a canary; promotion is reconsidered only when a measured trigger flips:
1. entries working set outgrows RAM (cache hit ratio materially below 100%),
2. sustained worker CPU pressure (>70% of a core through working hours),
3. stitch checkpoint lagging real time at peak.
Preconditions then: the pending round-trip (18ab) + a grouping-level audit. Until a trigger flips, the daily check is a canary read, not a promotion countdown; any DIVERGED still comes to Claude.

## Operational conventions worth knowing on the server

- Deploy: `cd /opt/RAG-Pipeline/RAG-PipeLine && git pull && PYTHONPATH=$PWD venv/bin/alembic upgrade head` then restart both services.
  `PYTHONPATH` is required (alembic/env.py imports `app`); the venv is `venv/`, not `.venv/`.
- `sudo` needs a password; service restarts must be run by the user, not over BatchMode ssh.
- The worker journal is readable WITHOUT sudo: `journalctl -u fastapirag-worker`.
- The DB clock and app host clock have drifted before; the sealer horizon and `db_today` deliberately use the DATABASE clock.
- `pg_stat_user_tables` counters update asynchronously and are cumulative since the last reset; and `LIKE 'x_2026%'` patterns miss `x_default`, which is where NULL-key and out-of-range rows live.
