## Incidents fixed this session, where documented

These matter for resuming because their fixes carry conventions a future change must respect.

1. **Truncation outage.** 49 analytics windows dead-lettered on `StringDataRightTruncationError`; the normaliser was missing Stage 2's `_cap_over_length` port. Fixed in `f2f135e`; the cap reads widths from the ORM mapping, never a hardcoded list.
2. **Unbounded fold runs.** Coalescing with `gap = 2 * pad` merged eight daily tickets into one 8-day transaction that exhausted the 30 s statement timeout. Fixed in `3742f1d`: merge for correctness (gap 0), then split into 6 h slices (`analytics_max_window_seconds`), fold timeout 120 s (`analytics_fold_statement_timeout_ms`). Tickets are claimed on the LAST slice only.
3. **R3 read amplification.** `_read_response_entries` was 96% of the read cost; now skipped for transactions whose Stage 2 `row_fingerprint` is unchanged, guarded by `_NORMALISE_VERSION`. Bump that constant if `normalise` or `payload.extract` changes what a fact contains.
4. **S4 shadow divergence.** Every seeded run diverged because out-of-scope streams were seeded and carried entries were replayed. Fixed in `d0c98b5`: seed only the `freed` set, dedupe carried rows, report `out_of_scope`. Section 18p has the full mechanism.
5. **The audit trail of the truncation incident** (55 dead-lettered tickets) was exported to `/opt/RAG-Pipeline/RAG-PipeLine/logs/abandoned-tickets-20260825-2302.json` and then deleted, after verifying the ranges were fully rebuilt.

## S4b: SUPERSEDED on 2026-08-27 - read section 18q

The 7-day gate above proved unmeasurable: 1,411 post-fix shadow runs, zero divergences, `seeded_streams = 0` in every one (structural - a rebuilt transaction's entries are inside the window, so its stream always fails the floor guard).
`stage2_stream_lookup` stays `shadow` forever and is never set to `on`; its retirement is planned as P5 in `~/.claude/plans/2026-08-27_01-30_stage2-streaming-endstate-and-crosspad.md`.

What shipped instead (chunks 64 + 65, section 18q):

1. **Cross-pad healing** = bounded backward window extension in `regroup_window` (`_cross_pad_floor`), new setting `stage2_cross_pad` = off / shadow / on, DEPLOY AS `shadow`.
   Review surface: `journalctl -u fastapirag-worker | grep "cross-pad"` (candidates, would-extend seconds).
   Expect near-silence: the population is structurally ~empty at current settings (span must exceed 600 s; measured max 363.7 s); it exists for backfill healing and future span growth.
   Owner flips it to `on` after reviewing the shadow lines (their chosen manual gate).
   A `CrossPadSpanExceeded` dead letter is a genuine span-over-pad conversation: repair with a manual full regroup of the span.
2. **The frontier defect fix** (was LIVE since S3 deployed): `consume.py` `_FRONTIER_COLUMN` moved to `updated_at` and the fold now reads through the constant.
3. **Notification dedup key** now `(rule, txn, status)`: a status change re-alerts; an unchanged transaction still dedupes.

Post-deploy verification 2026-08-27 additionally found and fixed (chunk 66): the reconcile worker had reported 127-463 false `rollups_vs_facts` findings every hourly pass since it was enabled - a window-boundary artifact (buckets only partially covered by the rolling window disagree by construction).
The reconciler now compares only whole buckets, and `analytics_reconcile_window_hours` widened 24 → 48 so the daily grain is actually audited.
After deploying that fix, a healthy pass reports exactly `entries_vs_assignments=6` - the known Aug-5 orphan baseline (ten entries in two truncated files, repairable at will with a windowed regroup over 2026-08-05 05:30-05:45 UTC).

**RESOLVED 2026-08-27 (chunk 67, section 18r): the orphaned-entry leak.**
Root cause found and fixed: grouping ignored which SERVER a log line came from, so one picker hitting both app servers within milliseconds cross-bound into chimera transactions, and the displaced request minted the chimera's own id and was clash-skipped forever.
Grouping is now server-scoped; _DERIVE_VERSION bumped to 2.
The backlog repair was completed on 2026-08-27 (full rebuild, worker stopped): all orphans stitched, chimeras dissolved, facts restated - day totals rose slightly because mashed operations count as two again.
LESSON RECORDED: `POST /logs/regroup` (the inline full rebuild) was REMOVED (chunk 68) - it cannot survive its own duration over HTTP and races the live worker.
The tracked replacement SHIPPED (chunk 69): `POST /logs/regroup/full` (or Manage -> Maintenance in the frontend) - 202 + run id + poll, subprocess-isolated, and the tenant's workers pause automatically while it runs.
The manual stop/script/start procedure is no longer needed.
Also: after any rebuild that emptied `log_transactions` first, the analytics re-ticket span must derive from `log_entries`, not from the (empty) transactions table.
Original finding, for the record:

Top open engineering item found once the noise was gone (2026-08-27): the orphaned-entry leak.
The clean reconciler view revealed 5,353 unassigned entries for tmp-live (not the "handful" earlier believed), growing ~300/day since ingestion began on 2026-08-10 - full conversation shapes (requests, bodies, responses), heavy in transaction type 005001.
Mechanism confirmed from the journal: 185 "skipped builder(s) with an already-sealed id" warnings in ~1.5 days - `_persist`'s out-of-order clash skip (`derive_transactions.py:756-758`) fires on LIVE traffic, not only on bulk ingest, and each skip leaves that builder's entries unassigned forever.

Repair for the backlog once root-caused: a full regroup (`POST /logs/regroup`) reassigns everything cleanly (all transactions freed, no clash possible).
This predates iteration 2 (chunk 49's docstring already knew "roughly 1,000 orphaned entries" on 2026-08-22).

## Operational conventions worth knowing on the server

- Deploy: `cd /opt/RAG-Pipeline/RAG-PipeLine && git pull && PYTHONPATH=$PWD venv/bin/alembic upgrade head` then restart both services.
  `PYTHONPATH` is required (alembic/env.py imports `app`); the venv is `venv/`, not `.venv/`.
- `sudo` needs a password; service restarts must be run by the user, not over BatchMode ssh.
- The worker journal is readable WITHOUT sudo: `journalctl -u fastapirag-worker`.
- The DB clock and app host clock have drifted before; the sealer horizon and `db_today` deliberately use the DATABASE clock.
- `pg_stat_user_tables` counters update asynchronously and are cumulative since the last reset; and `LIKE 'x_2026%'` patterns miss `x_default`, which is where NULL-key and out-of-range rows live.
