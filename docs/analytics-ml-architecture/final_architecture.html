Why the design looks unusual

log_transactions is not an append-only table and not a time series. It is a mutable projection: each record is stitched from roughly 15 raw log lines, and when a late line arrives the row is deleted and rebuilt, possibly with different values. Superseded 2026-08-23 - see section 18: the row stays mutable, but Stage 2 is moving to UPDATE in place. The churn figures below describe the content, which is unchanged; they stop describing the storage.

98.7%of rows written more than 5 min after their own log lines
1.7 haverage gap for sealed rows
5.4 hworst observed gap
0.6%built promptly, within 60 s

So rebuilding is the norm, and a row is not final until hours after the event. Two conclusions follow, and they rule out the two obvious designs.

  • Simply adding numbers up is wrong. A rebuilt row would be counted twice, producing plausible-looking wrong totals with no error.
  • Waiting for rows to settle is also wrong. Sealing is measured against the newest log timestamp, not the clock (derive_transactions.py:535-538), so the wait has no bound and stops entirely whenever ingestion pauses.

Consequence for implementation

The version hash on each contribution is load-bearing, not an optimisation. At a 98.7% rebuild rate almost every recheck must be absorbed as a no-op by a matching fingerprint, or the system produces a constant stream of pointless aggregate writes.

Corrected 2026-08-21

An earlier revision said "the second is the live path", running every 70 seconds. Both halves are wrong. app/background.py:84-164 registers eight background loops and regroup_incremental is in none of them; the only automated Stage 2 driver is log_stitch_worker, which imports finalize_pending alone (log_stitch_worker.py:37). regroup_incremental is reachable only from POST /logs/regroup?incremental=true (logs.py:358) and the tail of the date-range delete (logs.py:728).

The error came from three further stale comments in the same file, worth reporting upstream together:

LocationWhat it saysReality
derive_transactions.py:11-13 "regroup_incremental(db) LIVE path ... This is what the worker runs" no worker calls it

Why it matters. Because regroup_all and regroup_incremental never pass cont, they receive EMPTY and recompute ids from the anchor entry. The _resolve_ids docstring implies that is safe because they do not free transactions, which is untrue: both delete from log_transactions.

The two defects compound in opposite directions, which is why both are listed. The docstring understates how many paths delete, so a reader thinks id stability is protected everywhere. The three "live path" comments overstate which path runs, so a reader thinks the unprotected path is the hot one. Together they produce exactly the wrong mental model: id churn everywhere, on the busiest path. The truth is the opposite.

This is a comment defect, not a code defect. Recomputing ids for unsealed rows may be a deliberate scoping choice. But the comment gives a false reason, which is worse than giving none.

Why an id change costs this design nothing

The strongest argument for the range diff. Same three events, two methods.

✗ Look up receipt 47 and update it
10:00Pick recorded as receipt #47, 30 units.
10:12Books redone. Same pick, now receipt #91.
→Nothing looks for #47. It never existed to update, so its 30 stays. #91 adds another 30.
total60Wrong, permanently, no error.
✓ Compare the whole 10:00-10:30 window
10:00Pick recorded as receipt #47, 30 units.
10:12Books redone. Same pick, now receipt #91.
→#47 absent from source, so reverse −30. #91 absent from our records, so apply +30.
total30Correct, with no special handling.

An id change is simply two rows of the diff table firing together:

SituationActionOn an id change
id in both, fingerprint equalskip
id in both, fingerprint differsreverse + apply
id in our facts, absent from sourcereversethe departed id
id in source, absent from our factsapplythe arrived id

Identical handling to a merge, where two records combine so an id disappears, and to a split, where one divides so an id appears.

The failure mode this avoids

A per-id update, UPDATE ... WHERE source_id = ?, passes a test where a quantity changes and fails silently when an id vanishes. Nothing looks for the departed id, so its contribution stays in the total forever and no error is raised. That is why the range diff is a hard requirement, and why verification item 4 exists separately from item 3.

The one real consequence, corrected 2026-08-21

continuity.py reads as though ids are now stable, and on the automated path they are. The path that runs unattended is regroup_window, and it does pass cont (:858-861, :895), so ids are preserved through every ordinary rebuild.

An earlier revision said the opposite: that ids were "stable on backfill only" and therefore analytics_fact_ledger would churn more than continuity.py suggests. That followed from believing regroup_incremental was the live path, and it is wrong in the safe direction. Expect less ledger churn than the earlier estimate, not more.

Id churn is still possible, but only when someone invokes POST /logs/regroup or the date-range delete, so it is operator-driven and occasional rather than continuous. The range diff absorbs it either way. Nothing about the design changes; only the volume estimate moves, and it moves down.

If the deferred update-in-place change ships, ids stop churning entirely. That is the same upstream change that would break the retention cursor in F6: one decision, two effects on us.

So stability holds for the automated path, plus backfill and repair. It does not hold on the two manual endpoints, where an unsealed record gaining a late REQUEST line will change id.

Impact on this design: none, and that is the point

The range diff reverses a vanished id and applies a new one, so an id change is handled exactly like a merge or split. This is further evidence that the range diff is mandatory and a per-record update would be wrong. It does mean the ledger sees more identity churn than reading continuity.py alone suggests.

Why this scheme and not the obvious ones

A 20-character prefix would break PostgreSQL

Once partitioning.py appends a date and the concurrent-index recipe appends columns, the 63-character identifier limit is exceeded. partition_name raises past the limit, so this fails at partition creation rather than quietly. Measured:

analytics_ also matches the form of the existing notification_ and log_ prefixes, where the repo uses a single domain noun.

Names are plural, because the repo is predominantly plural: log_entries, notification_rules, consumer_cursors, log_regroup_runs, saved_views, jobs, customers, against only log_entry_assignment, log_regroup_pending and logspace_presence.

analytics_pending_windows, not dirty_window. "Dirty window" is imported data-engineering jargon. The repo's equivalent table is log_regroup_pending, named for what is pending rather than for a term of art.

Why facts and not contributions

These are not synonyms, and the distinction is load-bearing.

CandidateWhat it impliesVerdict
contributions"what this row contributed to a total" too narrow: 47 of 49 methods carry no quantity. A GetAccessToken row contributes to no sum but still has a duration, status and operator.

But "ledger" is the right word for the other table

analytics_fact_ledger genuinely is append-only, one row per version, showing how each fact changed over time. That is what a ledger is. It also tells a reader what the table is for in a way that _history did not.

The plan's prose about "the contribution ledger with delta application" stays as it is. That phrase describes what the worker does; a table name should describe what the table contains.

Module names follow the tables. The repo pairs services/notifications/ with notification_* tables and notification_worker.py. The exact parallel is services/analytics/ with analytics_* tables and analytics_worker.py.

Still reversible

Renaming before Phase 1 costs nothing. Renaming after the first migration costs a migration. Confirm before any schema work begins.

Component detail

E4

Partition manager

persistence/partitioning.py, workers/log_partition_worker.py
statusExists, extended 2026-08-21 for per-table grain and keep-forever retention. jobProvision partitions ahead of ingestion, and drop what is past retention. Hourly, idempotent. ownsthe partition DDL for every partitioned table, and the retention policy

Listed here rather than left implicit under "exists" because every partitioned analytics table is registered with it, and a mistake in that registration destroys data no other component can rebuild.

Create provisions today through today + log_partition_precreate_days (14). This half must not fail quietly: an insert into a period with no partition fails outright, so an exhausted runway stops Stage 1 dead. Drop reclaims disk by unlinking a partition rather than DELETE + VACUUM, which is why these tables were partitioned at all.

What was extended, and why it had to be before Phase 1

The module was daily in every function: the name format, the FROM/TO bounds, the coverage arithmetic and the expiry comparison. Retention was a single setting applied to every registered table. This plan partitions seven analytics tables: five monthly (analytics_facts, analytics_fact_ledger, analytics_quality_issues, analytics_feature_sets, analytics_predictions), one yearly (analytics_daily_rollups) and one daily (analytics_hourly_rollups). Five of the seven are retained forever. Registering them under the old code would have done two silent, destructive things: created daily partitions instead of monthly ones, and had the worker drop the forever tables at 60 days, a whole month at a time. Raw data is gone at 60 days, so a dropped fact partition cannot be rebuilt from anything.

Three bugs only exist once grains do, and all three were fixed with the extension:

BugEffect if leftFix
expiry compared the partition's FIRST dayJanuary droppable on 2 March under 60-day retention, throwing away 30 in-policy daysexpired_days compares period_end
the retention gates protected a DAYa window or reader working on 15 August would not hold the August partitiongates keyed on (table, period_start) and compared against the period's span

Both collections are empty today. Their retention arithmetic is unchanged, and at a daily grain period_start and period_end are the identity, so every new comparison collapses to the old one. All three are explicitly grain=Grain.daily at their definition site, and a test asserts they still are, so a future change to one of them fails loudly instead of reshaping live retention.

What Phase 1 must decide per table: grain, retention, and the DEFAULT partition. The third is not optional: every partition key in this schema is nullable, and without a DEFAULT an insert of a NULL key fails outright and takes the batch with it.

Why site 5 is the awkward one

The full wipe deletes jobs and lets the database remove the transactions:

# api/v1/logs.py:681-682
res = await db.execute(delete(Job).where(
    Job.customer_code == customer, Job.document_type == DOCUMENT_TYPE))

They disappear because of log_transaction.py:64:

job_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("jobs.id", ondelete="CASCADE"), index=True)

So there is no log_transactions statement to attach a ticket to: the removal happens inside PostgreSQL. The ticket must be published before the delete(Job), while the rows are still readable, and it must cover the tenant's whole span rather than a computed window. The endpoint already counts the transactions first (logs.py:675-676), so the span is one extra aggregate beside a query that is already being run.

Why this cannot be deferred

analytics_facts is retained forever and raw data is dropped at 60 days. A purge with no ticket leaves the purged contribution in every total permanently, with no error and, after 60 days, nothing left to recount against. It is the only defect in this design that erases its own evidence.

Insert-only. No foreign key, no unique constraint a retry could violate, no trigger, because a failure here fails ingestion. Table shape mirrors log_regroup_pending field for field. It is a separate table, because consumed_at is single-consumer and Stage 1's tickets never cover regroup_incremental.

The diff, which is the heart of the component:

The third row is why the diff must span a range. A merge makes one id disappear, and a per-id update would never look for it, leaving its contribution stranded permanently.

Failure policy

A poisoned row is quarantined and the tenant continues. A failed run leaves tickets open, bumps attempts, and dead-letters at the configured maximum. One bad row never halts a tenant, following the precedent already set in consumer_cursors.py.

analytics/registry.py

The thirteen fixes

F1 to F11 are defects found in the earlier plan by code reading and live measurement. F12 and F13 were found on 2026-08-21, after this document was written, by grepping for every statement that removes a log_transactions row rather than reasoning from the rebuild paths. Both are coverage gaps of the same kind, but they need different fixes, which is why they are separate entries. Red is blocking, amber serious, blue smaller.

F1

Ticket bounds must come from the delete, not the new lines

defect
regroup_window has explicit bounds, but regroup_incremental deletes WHERE sealed IS FALSE with no time predicate. Bounds taken from incoming lines would miss an older unsealed row caught in the same delete, which then drifts permanently.

priority corrected 2026-08-21
An earlier revision said "this path runs every ~70 seconds", which is wrong: regroup_incremental is reachable only from POST /logs/regroup?incremental=true and the tail of the date-range delete. It is an operator action, not a cadence, so F1 is no longer urgent. It still has to be done, because the endpoint exists and deletes without a time bound, but it can follow the automated path rather than lead it. The regroup_window publish site is the one that matters for continuous correctness, and its bounds are already computed at :837-838. Note the select at :779 returns ids only, so it needs started_at added, and the ticket must be inserted before the commit at :787.

fix
Every publisher computes bounds from the set actually freed. The unsealed ids are already selected before the delete, so take min and max started_at over that same set and publish it padded. Empty set means no ticket.

invariant
No record may be deleted by any path without a committed ticket whose range contains its started_at.

F2

Reconciliation must also check completeness against log_entries

defect
The proof of correctness recomputes from log_transactions. Both sides read the same projection, which is currently missing ~1,000 orphaned lines, so reconciliation passes while under-counting.

fix
Two independent scheduled checks. First, totals against a recount. Second, a count of log_entries rows past the abandon window with no row in log_entry_assignment, grouped by source file and program. Surface both in the state row and on the dashboard.

act now
Run a scoped regroup over 2026-08-15 to 2026-08-17 for the two named files, and find the cause before assuming a regroup fixes it, because whatever caused it will recur.

F3

Ledger identity must mirror the source constraint

defect
Keying contributions on the record id alone. Source uniqueness is (id, started_at), and two rows can share an id in different partitions "silently and undetectably". A ledger keyed on id alone would collapse them and under-count.

fix
Key on (customer_code, source_transaction_id, source_started_at). Zero duplicate pairs exist today; the extra column costs nothing and removes the failure mode.

F4

Freshness needs two numbers, not one

defect
The 5-second target measures how far analytics lags the projection. But records are not final for 1.7 h on average. The screen could truthfully say "updated 2 seconds ago" about a number still due to move, which manufactures false confidence.

fix
Copy freshness: seconds between the analytics watermark and the source watermark. Settledness: the share of contributing records still unsealed, and the age of the oldest. A window with unsealed contributors reads as provisional, not stale, because those mean different things to an operator.

F5

The status endpoint must read exactly one row

defect
The browser polls status every 2 seconds per tab across four web workers, and the response includes counts over other tables. The cheapest request becomes the most frequent expensive one.

fix
The worker writes every status field into the single warehouse_analytics_state row each cycle. The endpoint is one key read plus an ETag. A test asserts it issues exactly one query.

F6

The retention bookmark must publish a write-time position

defect
Retention gating uses a cursor measured in write time, but the worker is driven by event-time ranges and has no natural write-time position. Unresolved, it either publishes nonsense or gates nothing, and the second loses data during the backlog that caused it.

fix
Track the maximum created_at seen among fully processed rows and publish the minimum across tenants under analytics:warehouse-v1. A ticket is only acknowledged once its whole range is diffed, so every row inside it has been read.

watch
A deferred team change would switch the delete-and-reinsert to an UPDATE. Then created_at stops moving and this fix breaks silently. Keep the cursor field a single named constant so the switch to updated_at is one edit. That change would also collapse the 98.7% figure this plan is sized against. This watch fired on 2026-08-23 - see section 18. The switch is now a live obligation, not a hypothetical.

F8

Zero-quantity picks are attempts, not consumption

defect
A share of pick confirmations record zero units and still say success, typically an empty location. Counting them as picks inflates productivity.

corrected 2026-08-21 (C4)
Was a single figure of 9.2%. Measured now, and the denominator matters: 8.29% of ConfirmPickLine alone (1,333 / 16,075), and 7.47% across all three quantity-carrying methods (2,056 / 27,511), which is what the consumption metric reports because its filter spans all three. The two are not interchangeable.

fix
Three counters, all stored in every rollup: quantity (sum of units), pick_count (confirmations above zero), attempt_count (all confirmations). The zero-pick rate derives from the last two and is a first-class metric, because it names specific empty locations and replaces the fill rate this data cannot support.

Add daily and monthly grains; derive weekly

defect
Hourly and lifetime totals only. A month-to-date question means summing about 1.08 M hourly rows, roughly 2.7 seconds and growing.

fix

F10

Keep contribution history, or machine learning is impossible later

defect
The ledger keeps only the latest value per record, so a rebuild overwrites the previous one. A training set built from it is not reproducible: the same query returns different data next week, no experiment can be replayed, and nobody can explain an old forecast. Discarded versions cannot be recovered.

fix
Two tables. warehouse_consumption_contributions holds the latest value and serves the delta computation. warehouse_consumption_contribution_history is append-only, one row per version with its revision, retained longer than raw data. Training sets pin a revision and become reproducible exactly.

defect
The exit criterion requires holding at 100× the measured rate, roughly 78,000 records an hour, with no way described to generate that without polluting real data.

fix

F12

Two API delete paths also remove transactions, and both must publish a ticket

added 2026-08-21
N1 originally listed three publish sites, all in derive_transactions.py, derived from "where does Stage 2 rebuild". The correct question is "where does a row leave log_transactions", and that has five answers: the three rebuild paths plus both halves of DELETE /logs/data.

defect
Date-range delete (logs.py:723) issues an ordinary delete(LogTransaction). The regroup_incremental call that follows at :728 does not cover it, because those bounds come from the freed unsealed set and these rows are already gone.

defect
Full wipe (logs.py:681-682) deletes jobs and the rows go via ON DELETE CASCADE (log_transaction.py:64). There is no log_transactions statement to hook, so the ticket must be published before the delete(Job), covering the tenant's whole span.

fix
Publish from both, per the table in N1. Severity: this is the only defect in the design that erases its own evidence. A purge with no ticket leaves the purged contribution in every total permanently; analytics_facts is kept forever while raw data is dropped at 60 days, so after 60 days there is nothing left to recount against and no error was ever raised.

Retention's own partition drops (log_partition_worker.py:146) are deliberately NOT in this list: analytics keeps its history after raw data expires, which is the point of verification item 9.

F13

A tenant purge must remove that tenant's analytics rows, not correct them

added 2026-08-21
logspace_cleanup.purge_logspace deletes the tenant's jobs (logspace_cleanup.py:114), and log_entries and log_transactions go with them via ON DELETE CASCADE. Reached two ways: DELETE /api/v1/customers/{code}, always available, and the E6 auto-expiry worker, which is off by default (logspace_cleanup_worker_enabled: bool = False). Section 6 previously asserted this path does not touch either table; that sentence is corrected.

why the fix differs from F12
F12 is about a window whose contents changed, so the answer is a ticket and a range diff. Here the tenant itself is going away, so correcting its totals is meaningless: the right action is to delete its analytics rows outright. Publishing a ticket would be actively wrong, since the worker would try to fold a tenant that no longer exists.

fix
Add every analytics_* table to the purge's cascade map. That file already maintains the map explicitly and says why, at logspace_cleanup.py:7-19: "so this stays correct as the schema grows". None of the analytics tables can rely on a cascade: they key on customer_code, a soft tenant key with no foreign key, exactly like log_entry_assignment, which that file already deletes explicitly at :110-111 for the same reason.

Severity: lower than F12, but it is a leak that grows. Nothing produces a wrong number; a purged tenant simply leaves its facts, ledger, rollups, tickets, state and quality rows behind forever, since every one of those is retained forever or pruned only on consume. Disposable log spaces are created per trial, so the orphan count grows with tenant churn rather than with data volume. It is also the one place where forgetting is invisible: the tenant is gone, so nobody looks at its rows again.

Metric registry

Decided 2026-08-18: this is the centre of the design

The user chooses what is measured and how it is sliced, from the interface, and the measure list is not fixed now. So nothing about dimensions or measures may be hardcoded into a rollup schema.

The consequence that cannot be deferred

If measures are chosen later, the fact row must capture every potentially useful field now. Raw data is dropped at 60 days, so a measure invented next year can only be backfilled across history if its fields were already being written. A consumption-only ledger would make "average duration by device" permanently impossible beyond 60 days.

So the ledger widens into a full fact row:

How a user-defined metric works

1
The user picks a dimension set, a measure, a filter and a grain in the interface.
2
That writes a definition row: identifier, dimensions, measure, filter, grains, and a draft/active/inactive lifecycle.
3
The worker begins maintaining its rollups on the next cycle.
4
A backfill populates its history from the fact table, which is only possible because the fact row is wide and retained. This is the payoff for the widening above.

Rollups are stored generically: a definition identifier, a fixed number of dimension slots and additive measure slots, rather than a bespoke table per metric. Adding a metric is a row plus a backfill, never a migration.

The honest limit

Fully arbitrary slicing over years cannot be pre-aggregated, because the combinations explode. Registered definitions are fast at any range. Genuinely ad-hoc exploration falls back to a bounded scan of the fact table, and the interface must show that distinction rather than silently running a slow query.

Also: a newly defined metric has no history until its backfill runs. That is a fact of the design, not a bug, and it should be visible in the interface.

Selection

Toggleable. A chosen set of types renders either as one series per type or as one combined total. Both are valid from the same rollup because counts and sums are additive. Percentiles across a selection need merged histograms, never averaged percentiles.

Verification

Grouped by consequence. Every item is a failure that produces a plausible wrong number rather than an error.

Correctness of the total

  1. Reconciliation: ledger totals equal a direct recount for the window.
  2. Completeness: lines past the abandon window with no assignment, by file and program. Currently non-zero, so this test starts red and that is correct.
  3. Restatement: rebuild an already-folded window and assert totals unchanged; change a quantity and assert the old contribution reverses exactly once.
  4. Merge and split: a merged record's vanished id reverses, a split's new id applies. A per-record update passes test 3 and fails this one.
  5. Ticket coverage: rebuild an old unsealed row through the automated path (finalize_pending → regroup_window) and assert a committed ticket contains it. Repeat through regroup_incremental, since that path derives its bounds differently (F1). Then once per site in the N1 table, all five (F12): fold a window, remove its transactions by that route, and assert the total returns to zero rather than staying at its pre-delete value. The two API routes are the ones that fail today, and the full wipe is the one a per-statement hook cannot catch.
  6. Identity: the ledger key includes source_started_at, and two rows sharing an id produce two receipts.
  7. Idempotence: the same fold twice leaves values unchanged.
  8. Crash safety: kill the worker mid-batch; no gap, no duplicate.

Data that cannot be recovered

  1. Retention independence: drop a 61-day-old raw partition; ledger, history and grains survive.
  2. Cursor gating: the position blocks retention while behind; a stalled worker is logged critical then stops blocking.
  3. Reproducibility: build a training set at a revision, restate a contribution, rebuild at the same revision, assert identical output.
  4. Rebuildability: delete a grain entirely and rebuild it from the ledger to identical values.
  5. Tenant purge completeness (F13): fold a window for a throwaway tenant, purge the tenant, and assert every analytics_* table has zero rows for it. Assert no ticket was published, since the fold target no longer exists.

Traps specific to this data

  1. Attempts versus picks: zeros excluded from pick count, included in attempts and the zero-pick rate.
  2. Additivity: monthly-grain metrics equal ledger-computed ones, including distinct count, p95 and average.
  3. Top-N is not composable.
  4. Local business date at 00:30 during BST lands on the right local day.
  5. Numeric fidelity end to end; comparisons numeric, never string.
  6. Placeholder rejection: quarantined with a reason, never dropped silently.

Registry and user-defined metrics

  1. Fact-row completeness: every listed field is populated wherever the source has it. This guards the one irreversible schema decision.
  2. A newly defined metric backfills correctly: define one for a combination never registered before, backfill, and assert it equals a direct aggregate. This proves user-defined metrics are real rather than forward-only.
  3. Selection is additive both ways, and percentiles come from merged histograms.
  4. Quantity measures are refused where the field does not exist, since 47 of 49 methods have none.
  5. ISO week boundaries during BST.

Performance and end to end

  1. Status is one query. Queries are prepared, worth ~100 ms each.
  2. A 12-month request resolves to monthly, never daily. Grain reads plan as index-only scans, with query-plan proof.
  3. Load: synthetic tenant at 100× the measured rate, worker lag inside target.
  4. In the real interface: a live pick updates within target; a window with unsealed contributors reads as provisional; empty and loading states, fractional formatting, light and dark all checked.

18. Stage 2 redesign: the deferred update-in-place change

Approved 2026-08-23. This records a change to the upstream pipeline, not to the analytics platform - but sections 2, N3, F6 and Flow F all already track it as a pending dependency, and it removes premises this design rests on.

Nothing in sections 1-17 is retracted. They describe the platform as built, against a Stage 2 that delete-and-reinserts. This section describes what Stage 2 becomes, and exactly which of those premises stop being true.

What was implemented before

Stage 2 is a window re-deriver. A ticket arrives, regroup_window deletes every transaction anchored in [lo − 900 s, hi] regardless of sealed, re-reads the entries the delete just made unassigned, re-groups them from scratch, and re-inserts everything.

That shape is deliberate, and it earned three properties this platform was designed around:

  • Back-filling into a sealed region is lossless, because sealed rows are re-derived too.
  • A crashed worker needs no recovery - all grouper state is derived per cycle.
  • A wrong grouping self-heals on the next of ~22 passes, which is why no split-that-should-have-merged has ever been observed.

The re-deriver's third property - a wrong grouping self-heals on the next pass - is being given up, and it is given up by S3 rather than S4: once an identical rebuild writes nothing, nothing revisits the row.

Two things the verification pass added

_DERIVE_VERSION is not optional, and it is easy to leave out. S3 skips a rewrite when the stored fingerprint matches the recomputed one. Decisions

Capture response scalars for all 49 methods. Measured over 400 live responses: 947 scalar values against 9 non-scalar, across 145 distinct keys. Cost is attributes growing from 806 to roughly 2,000 bytes - about 1.8 MB/day, roughly 3 GB over five years, against a 4.5 GB database that already generates 9.6 GB of WAL per day. The upside is unrecoverable, which is the same reasoning section 11 uses for the fact row's width.

Per-record expansion stays selective. records[] is where the ~200k rows/day is, so it is opt-in per method. The 60-day retention window is the safety net: you can always expand a method you did not pick, provided the scalars were already being captured.

Field capture is an allowlist that DISCOVERS

_SENSITIVE (derive_transactions.py:45) is a five-word denylist, and the two most frequent response keys across all 145 are AccessToken and M3UserCredentials. A denylist guarding a KEEP_FOREVER table is the wrong shape - one renamed credential field becomes permanent. But a static allowlist would silently drop new fields, losing the future-metric history the capture exists to buy.

So an unknown key is neither captured nor ignored: its name only is recorded, captured = false, and surfaced for review. The allowlist becomes data - one row per (method, field), self-populating rather than hand-maintained. Storing only the name means the discovery record itself cannot leak a value.

The payload goes to analytics_facts, NOT to log_transactions. Merging it into the projection would widen the exact hot table S3 exists to make cheaper to write. Instead N3 reads the transaction's entries alongside it and passes them to N2, which stays pure because the reading happens in N3. That keeps this change entirely analytics-side.

Namespace, never flat-merge. Request and response both carry ItemNumber; a flat merge silently drops one. Response fields are prefixed on capture (resp.QuantityOnHand, mi.STQT) so fold's row.get(field) keeps working unchanged and a collision is structurally impossible.

Open, not yet decided: whether the per-record grain is a new table or a second row type in analytics_facts. A separate table keeps the existing fact row's meaning clean but doubles the fold path; the answer depends on how rollups.recompute handles two grains, which has not been looked at yet.

The hand-off is a durable row rather than a push, because the worker is a separate systemd process and gunicorn recycles its workers. A push would lose the hand-off on any restart; a row survives it. derive_transactions.py:805 states the property directly: "Before the commit, so ticket and change are atomic (invariant 3)." So a rebuilt transaction with no ticket cannot occur.

The consequence for the registry. Because a ticket carries a time range and no transaction identity, provisioning a transaction does not create a stream - it changes what the consumer does with windows it was going to process anyway. Flipping Capture on therefore needs no separate backfill machinery: write the registry row and publish tickets across the retention range in one commit, and the ordinary path does the rest. The range diff reports every already-folded transaction as unchanged and inserts only the newly captured one, and _coalesce (consume.py:194) merges adjacent tickets so 60 days is a handful of runs, not sixty.

That is why the queue stays one ticket per (customer, window). Segregating it per transaction would cost a per-transaction cursor, lock and reaper to buy the ability to skip work that must not be skipped.

The invariant a registry write must honour

The registry row and its tickets must be written in the SAME commit, exactly as Stage 2 does. Row first, commit, then publish leaves a transaction marked captured with no tickets - silently absent until some unrelated rebuild happens to touch those windows. The natural shape of an API handler is "save, then react", so this is easy to get wrong.

Why C is cheaper than it looks, and the one thing it must not get wrong

Promotion copies; it never moves. normalizer.py:228-231 puts attributes on the fact first and only then reads out of it with attributes.get(key). The key survives promotion, so a metric still written as attr:resp.BaseUoM keeps resolving after base_uom exists. That retires the risk of one dimension splitting across two representations - the two paths read the same surviving value, they do not compete.

The fingerprint makes promotion self-healing. _fingerprint (normalizer.py:139) hashes every field not in _NOT_FINGERPRINTED, which includes the promoted columns and the attributes blob. So adding a promoted column changes the fingerprint of every fact; the range diff reports those transactions as CHANGED rather than unchanged, reinserts them with the new column populated, and the rollups recompute off the rebuilt facts. Promotion therefore needs no hand-written backfill. Without it, a promoted column would be NULL on every historical fact while the stored rollup still held the value, and rollups_vs_facts would report drift on every historical bucket - a permanently red auditor, which is worse than no auditor.

The cost this makes explicit. Promotion re-folds the retention window, and so does R3, since adding response scalars to attributes changes every fingerprint too. Both need tickets published across the retention range exactly as a Capture flip does. This is correct behaviour rather than a problem - it is what populates the new column on old facts - but it should be a deliberate, announced operation, not a side effect of a save button.

The invariant C must not get wrong

Both read paths must normalise identically. The attr: path extracts text from JSONB; the promoted column goes through _as_text. If those differ by so much as trimming or case, the same base UoM lands in two different rollup rows and one item's total splits in half. One helper, used by both, asserted by a test that folds the same fact down each path and compares the stored dimension byte for byte.

Still open, and not specific to C. Whether an ACTIVE definition's dimensions may be edited at all. dim1..dim4 are positional and interpreted through definition.dimensions, so changing that list changes what existing rollup rows mean while their values stay as they were. The safe rule is that dimensions and measures are immutable once active and an edit forks a new definition, which is what status and backfilled_through already exist to support. Promotion does not need this resolved - renaming attr:resp.BaseUoM to base_uom yields the identical dimension VALUE, so stored rollups stay correct - but a genuine dimension change does.

Worth stating either way: four dimensions at hourly grain multiplied by item-number cardinality is where the rollup tables actually grow. DIMENSION_SLOTS caps it at four for that reason rather than by accident.
