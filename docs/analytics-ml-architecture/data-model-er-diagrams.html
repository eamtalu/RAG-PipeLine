Matrix Pipeline Data Model

The database is one assembly line with five stations. Each station reads the table the previous one wrote, writes its own table, and leaves a ticket in a small queue table for the next station. Only the raw log lines are ground truth. Everything after them can be rebuilt.

enforced foreign key soft reference, no constraint ground truth, append-only ticket queue between stations saved-state cache, not truth shadow lane, reads but never writes

Station 1
Collection: pulling files over SSH

One row in log_ssh_sources is one WMS server to poll. The fetcher downloads only the bytes that are new since the checkpoint, saves them to disk, and records that byte range in log_source_objects. The checkpoint moves forward in the same database transaction, so bytes are never skipped and never downloaded twice.

  1. Pick the customers and sources. The supervisor keeps one loop per customer that has an enabled source. Each tick reads the enabled sources and, afterwards, writes health and the circuit breaker back to the same rows. ssh_log_fetcher.py:117, remote_fetcher.py:555
  2. Look at the server. Take a per-host lock, open SFTP, list files matching the glob, hash the first bytes of each file. remote_fetcher.py:411
  3. Decide per file from the checkpoint. Unchanged: skip. Same content seen under another name after rotation: skip. Rotated or truncated: re-read from zero. Otherwise read from the saved offset. A pure function with no I/O. remote_fetcher.py:354
  4. Queue and checkpoint together. Save the bytes to disk, insert one pending log_source_objects row, upsert the checkpoint to the new offset, commit once. remote_fetcher.py:141
  5. Lease. The parse worker takes the oldest due pending row with a skip-locked update and a lease expiry, so a crashed worker's row is reclaimed later. log_parse_worker.py:68
  6. Parse. Create a jobs row, run Stage 1 on the saved bytes, mark the object ingested with its entry count, delete the local file. Failures back off, and after the maximum attempts the row is abandoned with its error. log_parse_worker.py:227
  7. Manual fetch only. The dashboard button creates a log_ssh_fetch_runs row, runs the same fetch in the background with progress written to that row, and marks it completed or failed. remote_fetcher.py:733

How a rotated file is recognised

The checkpoint row carries two identities. The path is the unique key, (source_id, remote_path) at log_ssh_file_checkpoint.py:31, and answers "where do I resume in this name". The content signature, head hash plus size plus mtime, answers "have I seen these bytes before, under any name". This server uses rename-cascade rotation, where every file changes name on every rotation, so the second identity is what stops 100 files being downloaded again each morning.

  • Why the first 4 KB is a safe identity. A log is append-only, so once a file is past 4,096 bytes its head never changes, and a rename preserves the bytes, the size and the mtime. All three must match for branch 2, so a false skip needs a different file with the same first 4 KB, the same length to the byte, and the same modification time.
  • Below 4 KB the hash is not trusted. fp_reliable requires both the stored size and the current size to be at least 4,096, so a small file being appended to falls through to size and mtime and is never mistaken for a rotation.
  • The backstop. If a signature ever misfires, for example because the server rewrote the mtime on rename, the file is re-read from zero. Stage 1 hashes every raw line and inserts with ON CONFLICT DO NOTHING at parse_insert.py:46, so a re-read costs bandwidth and parse time but never a duplicate entry.
  • If the files had stable names. With date-stamped or ever-increasing numbers, a file keeps its name for life and branch 2 with its index would never fire. Branch 3 would still be needed for a file truncated or replaced in place, the newline trim for half-written lines, and the dedup as the backstop. The general form is kept because the WMS server chooses the rotation policy, not this code, and the cost is one 4 KB read per file per poll.

From remote bytes to a queue row, and back to entries

A log_source_objects row never holds bytes. The bytes are downloaded into memory by the SFTP read, written to a local chunk file, and only then is the row inserted pointing at that file. A row with status pending therefore means "saved on our disk, not yet parsed", never "not yet downloaded". The parse worker later leases the row, loads the file by its storage_key, parses it into log_entries, marks the row ingested and deletes the file. On the live server the whole cycle takes about two seconds.

Station 2
Stage 1: lines become rows

A worker picks up a byte range every two seconds, splits it into lines, and writes one row per line into log_entries. Then it drops a ticket into log_regroup_pending saying which time range now has new lines.

  1. Create the job. The parse worker inserts a jobs row for the object's saved bytes and sets it to parsing. log_parse_worker.py:227, parse_insert.py:84
  2. Load the bytes. Read the file at the object's storage key and decode it as UTF-8, replacing bad bytes rather than failing. parse_insert.py:88
  3. Parse in two passes, no database. Pass one splits the text into entries wherever a line starts with a timestamp. Pass two parses the header with one regular expression into user, thread, level, logger, method and message, then classifies the entry. ERROR level wins. Then the message prefix: REQUEST BODY, REQUEST, RESPONSE. Then the method: LogAPICall is an MI call, LogAPIResult is an MI result. A stored procedure text is sql. Everything else is info. Field extraction pulls the MI program, transaction, result and record count into columns and the request or response JSON into fields. m3_dotnet_parser.py:60 and :120
  4. Attach the tenant timezone. The log has naive local wall-clock times. The worker reads this customer's timezone and makes each timestamp a real UTC instant, with DST handled per date. This is the single choke point for every ingestion path. parse_insert.py:98
  5. Insert in batches of 200. Each row gets a fresh id and a SHA-256 of its raw text as entry_hash. The insert is ON CONFLICT (customer_code, entry_hash, timestamp) DO NOTHING, RETURNING timestamp, so duplicates are skipped silently and only the rows that really landed report their time. parse_insert.py:46
  6. Write the ticket and finish the job in the same commit. If anything was inserted, one log_regroup_pending row is added covering min to max of the returned timestamps, and the job is set to completed with the new-entry count. One commit for all of it. parse_insert.py:186
  7. Report back to station 1. The source object is marked ingested with the entry count and its local file is deleted. On failure the batch rolls back, the job is marked failed, and the object row records the error for retry. log_parse_worker.py:185

Why a jobs row exists at all

For the SSH path, log_source_objects already carries everything Stage 1 needs: customer, file name, storage key, status and retry budget. The jobs row the parse worker creates is redundant bookkeeping for that path. It is still there for two reasons, and neither is "the worker needs it".

  • 1. Enforced foreign keys. log_entries.job_id and log_transactions.job_id are real foreign keys to jobs with cascade delete, so an entry cannot be inserted without a job row existing first. log_entry.py and log_transaction.py, both ForeignKey("jobs.id", ondelete="CASCADE").
  • 2. Shared ingest record. jobs predates the log pipeline. It is the generic "one file was ingested" row used by the unrelated document-search pipeline (chunks, chunks_entity, embedding_queue all point at it) and by every other way log bytes enter the system. Stage 1 was written against a job and has never been split from it.

Station 3
Stage 2: rows become transactions

Stage 2 reads a padded time window of entries, groups them by server, thread and user, and writes one row per group. The group is the business action: when it started, how long it took, which user, warehouse and item, and whether it succeeded. The membership lives in its own table so that re-grouping never touches log_entries.

  1. Claim, coalesce, split. Every second the worker asks which tenants have an open, due ticket. For each tenant it reads all open tickets, merges ranges closer than twice the pad into runs, cuts runs into windows of at most six hours, and takes a per-tenant advisory lock per window. log_stitch_worker.py:106, derive_transactions.py:1536
  2. Pad. The window becomes lo minus 900 s to hi plus 900 s. The cross-pad extension may move the floor further back for a conversation that straddles it. Today it only reports what it would do. derive_transactions.py:1329
  3. Decide who is being rebuilt. Freed is every transaction that starts inside lo minus pad to hi, sealed ones included.   4. Publish the analytics ticket for the padded range, inside the same transaction, and before the early return, so a window that frees transactions and rebuilds nothing still tells station 4 to reverse their facts. derive_transactions.py:1390
  5. Read eligible entries. All entries in the padded range that have no owner or whose owner is in freed, in timestamp then file then line order. Nothing is deleted first. derive_transactions.py:1412
  6. Group in memory. An open conversation is keyed by (server, thread, user). A user-less line joins the thread's current conversation. What log_entry_assignment actually holds: one real conversation

log_entry_assignment is a plain link table. One row per entry, and every row of the same conversation repeats the same transaction id. Nothing else is duplicated: the entry's content stays in log_entries, the conversation's summary stays in log_transactions, and this table only says which entry belongs to which conversation and in what position. It exists because log_entries has no transaction column at all, so Stage 2 can regroup forever without touching an entry row.

  • Why a separate table and not a column on the entry. A column on log_entries was rewritten on every rebuild, about 55 times per entry, which caused the 5 August 2026 outage. Now a rebuild that changes nothing writes zero assignment rows.
  • Moving an entry is cheap. When regrouping moves an entry to another conversation, that is one small row deleted and one inserted, not an update of a wide entry row with eleven indexes. In Figure 4g, e6 joining B was: delete B's two rows, insert three rows e4, e5, e6 with seq 0, 1, 2. The entries themselves were never written.
  • seq is the timeline. The log viewer renders a transaction by reading its assignment rows in seq order and joining each to its entry. That order is also what members_fingerprint hashes, so a reordering counts as a change.

Gate, room, exit: where the owner map is used, and where it is not

"Rebuilding" a transaction means recomputing it in memory. Nothing is deleted or changed in the database when a transaction is freed. Its lines are loaded into Python, grouped again by the rules, given an id again, hashed again, and only the difference is written at the end. The owner map read from log_entry_assignment is used at two points and deliberately ignored at the one in between.

  • Why the gate keeps the 99 out. If a line of 2ec94540 entered the room, the grouper might seat it in a freed conversation. That conversation would be written with the line, but 2ec94540, which is not being rebuilt, would still claim it too. Two transactions owning one line, and 2ec94540's row describing 22 lines while 21 remain. Keeping it out leaves 2ec94540 exactly as it is until the window that covers 13:26 rebuilds it whole.
  • Why the room is blind. If the grouper were told "this line was in A", it would tend to put it back in A, and a mistake made once would repeat forever. Regrouping blind is what lets a wrong grouping heal on the next rebuild. It is also the reason the rebuild lane is trusted while the shadow head lane, which starts from saved state, is not.
  • Where ownership comes from in the first place. The room's decision, written down. The first time a line is seen it has no owner; the grouper seats it, the exit mints an id, and _persist writes one assignment row. That row is what the next window reads back as "owner".
  • "Freed" and "sealed" are different kinds of thing. Sealed is a column set by the sealer. Freed is this in-memory list, chosen by start time with no sealed condition, so 150 of the 161 freed transactions here were sealed and were rebuilt anyway. If their lines did not change they hashed identical and cost nothing.

Id resolution: inherit by plurality, mint otherwise

A transaction is rebuilt many times, so its id has to survive the rebuild. Before anything is freed, the window reads which transaction owned every entry in the read band. After grouping, each new group inherits the id of the freed transaction that owned most of its entries. A group with no freed predecessor mints a fresh id from the hash of its request line. Each old id can be handed to at most one group.

    votes = _votes(entries, continuity)            # only owners in `reusable` (= freed) count

def _claims(groups, fallbacks, continuity):
    claims = []
    for i, entries in enumerate(groups):
        winner = _plurality_owner(entries, continuity)
        if winner is not None:

            claims.append((-votes, fallbacks[i].bytes, i, owner))
    return sorted(claims)                          # strongest first, stable tiebreak

    taken, awarded = set(), {}

Analytics: transactions become facts

A worker consumes each ticket, re-reads the transactions in that window, and folds each one into a fact. Because a transaction is rewritten many times, the worker cannot simply add numbers up as they arrive. Each fact carries a fingerprint of its source. Same fingerprint, no write. Different fingerprint, replace the fact and push the old version onto the ledger.

  1. Claim and coalesce. Every two seconds the worker finds tenants with open, due tickets, merges overlapping tickets into disjoint runs of at most one day, and processes each run in its own transaction under a per-tenant lock in its own namespace. consume.py:1030, consume.py:844

Station 5
Rollups: pre-added numbers for charts and the chat agent

A rollup row is one metric, one time bucket, and up to four dimension values, with the sum, count, min, max, a histogram and, for a distinct-count measure, a sketch already computed. The levels form a cascade: the dirty hours are folded from facts, each local day is merged from its hourly rows when the tenant's zone allows it (the guard is explained below), and each month from its days. The API answers a chart by combining settled rollups for old buckets with a live scan of facts for the current bucket. Rollups store additive parts, never finished answers, so an average is computed at read time from sum and count.

  1. Choose the grain. Walk the definition's grains from finest to coarsest and take the first with at most 60 buckets and at most 100,000 estimated rows, which yields the coarsest grain that still resolves the window. A grain the definition never folded is never chosen, because it would return an empty chart that looks like zero activity. read.py:91
  2. Read the watermark once. The API reads the tenant state row and passes the analytics watermark into the planner. The planner cannot fetch it, by design. analytics.py:465, read.py:146
  3. Plan the two tiers. Whole buckets that end at or before the watermark come from rollups. The ragged edges of the request and anything after the watermark come from a live scan of facts. For the daily grain the boundary sits at the tenant's local midnight. An ad-hoc group-by, one not among the definition's dimensions, is served entirely live. read.py:146
  4. Read both tiers. Rollup points come from one prepared query over the requested dimension slots. Live points come from a fact scan capped at 200,000 rows and folded with the same fold function the writer uses, so a live edge and a settled bucket can only differ in freshness, never in meaning. A group the live fold saw but that contributed nothing to the measure is dropped, by the same _is_empty rule the writer applies before storing a row: no data is not a zero (chunk 93, after a live warehouse breakdown showed a flat zero series for the connectivity probes' empty warehouse). read.py:307, read.py:347
  5. Merge and answer. Role buckets are merged with add_roles. The response carries the grain, whether rollups were used, the live spans, additive roles per bucket and, since chunk 90, window totals per group merged on the server from raw roles so a distinct total is a union rather than a sum of estimates. Averages and standard deviation are derived by the caller from sum, count and sum of squares. A distinct count arrives finished as distinct_estimate, and a percentile as p50 and p95, read out of the 20-band log histogram by walking the cumulative count and interpolating inside the crossing band (chunk 92). Both are estimates: a sketch is about 1.6 percent off, a band is a factor of two wide, and the catalog marks both aggregations approximate. histogram.py:65 read.py:427, read.py:409, definition.py:410, definition.py:441

On the write side, inside the station 4 run, the diff names the dirty UTC hours and local days from both sides of every changed fact. Facts for the dirty hours are read once per run and folded into hourly rows for every active metric. Each dirty local day is then merged from its hourly rows, and each month from its days. The streaming pattern in full, and when it would be the right choice

Kafka Streams and Flink keep aggregates current by adjusting state as events arrive. Understanding how they make that safe is what tells you whether this pipeline should ever adopt it. The short version: they own three things this pipeline does not, and every one of the three would have to be built before a running total could be trusted.

The three terms, in plain words. Each of the properties in Figure 6f has a name from the streaming world. They are simpler than they sound.

Append once

An input is "append once" when every event is written to the end of the stream one time and is never edited or removed afterwards. A correction is a new event saying "the earlier one was wrong", not a change to the earlier one. A till receipt roll works this way: a refund is printed as a new line, the original sale line is never rewritten. This pipeline's source is the opposite. Stage 2 rewrites a transaction whenever a rebuild groups its lines differently: a merge deletes one row and enlarges another, a split does the reverse, and a full rebuild can rewrite a day. The stored row changes in place, so there is no stream of once-written events to key a running total on, which is why Station 4's range diff exists at all: it turns "what is stored now" and "what was stored before" into verdicts after the fact.

State and offset saved together

The offset is a bookmark: how far into the input the system has read. The state is the answer so far: the running totals. Saving them together means one indivisible snapshot, so after a crash the bookmark always matches the totals. Saved separately they can disagree, and a restart then either counts an event twice or never counts it.

Flink's checkpoint barrier is the mechanism: it flows through the stream and each operator snapshots its state store and the barrier's position in the same write. Here the bookmark is the ticket's consumed_at and the state is the facts, ledger rows and rollup rows, and all of them commit in one Postgres transaction with the stamp last, so for a single run this pipeline has the same guarantee. What one transaction cannot give is the other half of the streaming contract, the append-once input: a running total would have absorbed last week's version of a transaction, and no bookmark tells it that version was rewritten today. Rebuilding a bucket from current facts does not care what was absorbed before. consume.py:848

What adopting it would mean here, so the cost is visible when the question comes back:

  1. A change stream of fact versions. The ledger already records every version with a reason (insert, update, reverse), so the stream exists in a table. It would need a consumer position per key, which is the offset in the picture.
  2. A state store keyed by (metric, measure, dimensions, bucket). That is the rollup row itself. For sum and count the row is enough. For min, max, percentile and distinct the store must hold every contributing value, which is the fact table filtered to the bucket - the exact read the rebuild does today.
  3. Retraction handling. Every update becomes retract-old then insert-new, and a merge becomes retract-A, retract-B, insert-C, in that order, per bucket, for every metric. The ordering is what Flink's changelog semantics enforce and what would have to be written and tested here.
  4. An applied-version log to survive retries. Without the checkpoint barrier, a retried run must skip adjustments already applied: one row per fact version per bucket per metric, larger than the rollups themselves. Or the whole run stays in one transaction, which is today's design and removes the streaming latency advantage.
  5. Late data without limit. Flink windows close after an allowed lateness; here a transaction from months ago can be restated. Windows would have to stay open forever, which is again a store of every value.

Until 12 September 2026 a metric was a row someone inserted through the API and history came only from an operator re-folding a range. No new tables: two columns on analytics_metrics, three description or unit columns on the registries, one sketch column on the rollups, and one endpoint.

From then on the fold reads no fact before the bound, and the series read clamps a request to it rather than presenting older facts as this metric's. analytics.py:183, pending_windows.py:62, rollups.py:308, read.py:441

Forward only, so a backfill of an older range never drags it back. This replaces the earlier decision (D8) that the column stayed NULL forever. registry.py:140, consume.py:989

Distinct counts are a sketch, not a set. "How many different items were picked this month" is not a sum of daily counts: an item picked on twelve days is one item. Every other role adds; a distinct count only unions. The distinct aggregation therefore stores a HyperLogLog sketch, 4,096 one-byte registers, beside an exact count of rows that carried a value. The fold hashes the canonical value into the sketch, the cascade unions register by register, and the read path finishes the sketch into distinct_estimate in exactly one place, so no response ever carries the bytes. The catalog flags the measure approximate, about 1.6 percent error, and the window totals returned with a series are merged from raw roles on the server, so a distinct total is a union of sketches rather than a sum of estimates. In-repo, no dependency: the server has no hll extension. hll.py:49, hll.py:75, hll.py:85, definition.py:371, definition.py:425, definition.py:441, read.py:409

  • Why shape edits stop at activation. Rollup rows are keyed by the definition id. Changing dimensions or measures under an active id would leave rows nothing can explain, so the PATCH refuses with a 409 and the path is deactivate, copy, edit, activate.
  • Why a draft can become invalid. Create validates, so a draft is never saved invalid. But approval can be withdrawn afterwards: if a field the draft reads is switched off in the registry, activation re-validates and refuses with the field named, and the row stays a draft.
  • The percentile aggregation was finished on 13 Sep 2026. Auditing this section showed the histogram container, column and band-wise merge had existed since Phase 3 while nothing filled a band or read a percentile out, so a wizard-made percentile metric would have charted as no data. Chunk 92 completes both ends: the fold counts each value into one of 20 power-of-two bands (band 0 below 1, band i is [2^(i-1), 2^i), the top band clamps at 2^18), the bands merge through the same cascade as every other role, and public_roles reads p50 and p95 out at read time. An exact count_value sits beside the bands, as it does for distinct. histogram.py:32, histogram.py:56, histogram.py:65, definition.py:403

Platform
Tables that cross every station

These do not belong to one station. customers is the tenant registry that every customer_code column refers to, softly. Notifications watch log_transactions.updated_at through a cursor, and consumer_cursors stops retention from dropping a day a slow reader has not finished with.

Retention, step by step

  1. Create the runway first. For every registered partitioned table, create the partitions covering today through 14 days ahead. This runs before and independently of dropping, because a creation failure eventually stops ingestion while a drop failure only delays reclaiming disk. log_partition_worker.py:402
  2. Find candidates. A partition is a candidate when its last day is past its table's retention: 60 days for transactions, 61 for entries and assignments, 90 for hourly rollups, 365 for quality issues. Facts, the ledger, daily rollups and record facts are never candidates. log_partition_worker.py:103, partitioning.py:89
  3. Gate 2, open stitch work. Drop nothing an open, non-abandoned regroup ticket still overlaps. log_partition_worker.py:169
  4. Gate 3, live readers. Drop nothing whose end is past the minimum position among consumers that reported within 24 hours. A consumer silent longer than that is ignored and logged CRITICAL. consumer_cursors.py:85
  5. Gate 4, analytics health. If any tenant has an abandoned analytics ticket or a failed last cycle, hold the three source tables so a repair still has its input. The hold is capped at 14 days, then released with a CRITICAL log. Fails closed if health cannot be read. log_partition_worker.py:239
  6. Drop and report. Each surviving candidate is dropped as a table, then the remaining runway is reported every tick so a shortfall is visible before it bites. log_partition_worker.py:383

Notifications, step by step

  1. Tenant gate. Every query filters to tenants whose notifications switch is on. This one predicate is shared by rule loading, the delivery drain and the retention position, so they can never disagree. tenant_gate.py:31
  2. Rule engine. Per tenant, one query reads transactions by updated_at from the oldest of its rules' cursors up to 60 seconds behind now, only rows whose status is stable enough to alert on. Each streaming rule evaluates the rows past its own cursor. Digest rules summarise the most recent completed window. New events are published, and cursors advance in the same commit. engine.py:91, cursor.py:71
  3. Outbox. The dispatcher persists each event once, keyed by dedup_key, and creates one delivery row per target channel. Nothing is sent here. dispatcher.py:108
  4. Burst rollup. Past five alerts per rule in a five-minute window, further matches are stored as suppressed and one summary card per completed window stands in for them, through the same outbox. rollup.py:174
  5. Paced drain. Claim due deliveries with a skip-locked lease, round-robin across tenants, spend per-channel budgets of 20 per minute, batch 100, and send each in its own session. Failures back off from 30 seconds to one hour for up to 50 attempts, then dead. dispatcher.py:365
  6. Publish the position. After each tick the oldest active cursor across enabled tenants is written into consumer_cursors as the notifications position. Retention gate 3 reads it. consumer_cursors.py:122
