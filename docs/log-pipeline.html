How log files become transactions

A reference for the two-stage pipeline — fetch pulls files into a pool of timestamped entries; stitch groups them into transactions by time, not by file. Plus what the three timing numbers actually mean.

All of a poll's files are ingested first (each just drops entries into the pool and marks its own dirty time-range); the stitch then runs once per customer over those ranges — processing them cluster by cluster (next). So the order files arrive never affects grouping.

B. One poll → one stitch → N clusters

The single stitch does not take one big min(start)…max(end) window over every dirty range. It sorts the open ranges by start time and walks them: a range joins the current cluster only if it starts within 30 min (= 2 × the 15-min pad) of that cluster's running end — otherwise it opens a new cluster. Each cluster is then stitched and committed on its own.

Then, per cluster: pad ±15 min, split into ≤6 h sub-windows (_split_run — only bites if the cluster itself spans > 6 h), rebuild each sub-window, commit. A cluster that fails is isolated: its pending rows stay open for the next poll while every other cluster still commits.

Why this matters: a stale/orphaned range weeks in the past (e.g. a customer that went quiet) can never merge into today's live cluster, so it can't balloon the window into a multi-GB rebuild. It just sits as its own tiny isolated cluster.

poll → stitch
One poll fetches every file, then stitches once per customer. Never file-by-file.
stitch → runs
1 stitch = N runs (not 1). run == cluster — same thing in the code (runs = _coalesce_pending(...)).
run span
hi − lo of the cluster. Data-driven, no maximum — minutes in steady state, but hours or days after downtime (continuous logs keep coalescing).
the only cap
6 h caps the sub-window a run is sliced into for committing — never the run itself. A 14 h run → three commits (6h + 6h + 2h).

C. The three numbers

hi − lodata-driven

The run / cluster width = max(range_end) − min(range_start) of the coalesced dirty ranges — i.e. how much contiguous log-time piled up since the last stitch. Not a setting. On this box it's seconds-to-a-few-minutes in steady state (per-file ranges were 0.2–1.7 min); only catch-up (downtime, a big backfill file) makes it tens of minutes or more.

6 hourscap

A ceiling: never rebuild more than this in one bite — chop bigger backlogs into ≤6 h windows. log_regroup_max_window_seconds. Rarely hit (40 min < 6 h → one window).

±15 minsafety pad

Every rebuilt window is widened 15 min each side so a transaction is never cut at the edge. log_regroup_pad (= seal window). This is the overlap tax when you split.

E. When a cluster is bigger than 6 h — slice into windows

The 6 h cap only bites when a single cluster is wider than 6 h. Then _split_run cuts it into consecutive ≤6 h windows — each window is one regroup_window = one commit. 6 h is the maximum window size; nothing is ever cut finer than the data needs.

The commit count for a whole stitch

total commits = Σ over clusters of  ceil(cluster_span ÷ 6h)
40 min cluster

6 h cluster

24 h cluster
ceil(24 ÷ 6) = 4 windows
25 h cluster
ceil(25 ÷ 6) = 5 windows (6+6+6+6+1)
mind the gaps
Clustering happens first. 24 h of sparse data (>30 min gaps) becomes several clusters, each sliced separately — so count windows per cluster, then sum.

H. The guarantees, in one place

  • ◦Fetch ≠ stitch. Files only drop timestamped entries into a pool and flag a dirty time-range. Grouping happens later.
  • ◦Stitch by time, not by file. regroup_window reads every unassigned entry in a time window, ordered by timestamp — blind to which file delivered it.
  • ◦All files ingested first, one stitch pass after. Per poll: loop files → then a single finalize_pending over the coalesced ranges.
  • ◦Clusters, not one giant window. That one pass splits the dirty ranges by the 30-min gap rule into N clusters, each padded / ≤6 h-split / committed on its own — so a poison or stale cluster fails alone.
  • ◦Order-independent & idempotent. Deterministic uuid5 ids mean re-running a window rebuilds identical transactions — newest-first / oldest-last fetch is safe.
  • ◦Backfill is lossless. A late/old file marks its own old window dirty, forcing a delete-and-rebuild of exactly that slice.
