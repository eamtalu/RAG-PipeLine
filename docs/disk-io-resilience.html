Surviving a failing disk: bad-sector resilience

The production host runs on a spinning disk with unrecoverable bad sectors that cannot be replaced. This is how the ingest (write) path and the feed (read) path were changed so a dead block is skipped, logged, and stepped over instead of taking the whole system down — and the engineering ideas behind it.

A. What actually breaks

A bad sector is a physical region of the disk that can no longer be read. The kernel reports it as critical medium error … Unrecovered read error, and Postgres, when a query needs a row that lives there, raises:

could not read block 4571733 in file "base/16388/16613": Input/output error

Two dead blocks were hit: the log_entries table (the raw data) and its job_id index. The disk can't be replaced, so the software must treat a dead block as a fact of life: work around it where possible, and where not, fail that one small piece gracefully. Software cannot bring back the rows on a dead sector — this is graceful degradation, not repair.

B. The write / ingest path

Root cause of the outage: after inserting a file's entries, the pipeline computed the "dirty time range" to stitch by searching the whole table (SELECT min/max(timestamp) WHERE job_id=…). Finding the minimum means scanning from the oldest rows forward — straight across the dead block. So every ingest failed, and the poller retried it every ~2 minutes forever.

And if an ingest still hits a bad block (e.g. the dead index page during a write): the poller catches it per file — logs it, counts io_skipped, and moves on to the next file. One bad file never stalls the source or the poll.

A second, subtler failure on the same disk — slowness, not a dead block. Because the disk is failing and saturated, an index-heavy insert (each log_entries row updates ~11 indexes on a 40 GB table) started exceeding the 30-second statement_timeout — a guardrail meant for the web tier — so Postgres cancelled the insert (QueryCanceledError) and nothing ingested. Fix: the ingestion transaction relaxes that timeout for itself only (SET LOCAL statement_timeout = 0) so a slow insert can finish, while the web tier keeps its 30 s guard; batches were also shrunk (1000 → 200). A residual timeout is now treated as a skippable disk-fault, exactly like a dead block.

C. Before / after, side by side

before

Write path

Insert → scan the whole table for min/max → cross the dead block → I/O error → the entire file rolls back → job fails → poller re-tries every ~2 min → all ingestion stalled.

after

Write path

Insert with RETURNING → range from the just-written rows → no old-data read. If a file still errors, it's skipped + logged + counted, and the rest of the poll continues.

before

Read path (feed)

Open a day's feed → read the log entries → some sit on the dead block → unhandled 500 → the whole Manage/feed panel blanks out, even though the transaction list was fine.

after

Read path (feed)

Catch the I/O error → return the transaction list plus a clear notice ("some entries sit on a damaged sector"). The page still works; the failure is explicit, not a crash.

D. Isolation = smallest possible blast radius

The whole design is one idea repeated at every layer: wrap each independent unit of work in its own fault boundary, so a dead block can only ever take down that one unit — never its neighbours.

E. The engineering concepts (the parts worth keeping)

Fault isolation · bulkheads

Contain a failure to the smallest independent unit

Partition work into units that can fail alone — one file, one stitch window, one request — and wrap each in its own try/except. A fault is then bounded to that unit. Like watertight compartments on a ship: one floods, the ship still floats.

Fail-soft vs fail-fast

Skip-and-continue when the unit is non-critical and isolated

Fail-fast (abort everything) is right when continuing would corrupt state. Here, one unreadable file shouldn't stop the other files, so we fail-soft: mark it, log it, keep going. Choosing per situation is the skill.

Avoid the hazard

The cheapest way to survive bad data is to not read it

INSERT … RETURNING derives the range from the rows just written, so ingestion never scans the old region where the dead sectors live. Design each query to touch the minimum data it needs — it's both safer and faster (a ~7M-cost scan disappeared).

Transient vs permanent errors

Match the response to the error's nature

A dead sector is permanent for that block — retrying just fails again and stresses the disk, so we skip, not retry. Contrast the network layer, where a blip is transient and one retry heals it. And never auto-retry a non-idempotent write (it could double-submit).

Retry budget · dead-letter

Bounded retries, then park it — never retry forever

A stitch window can't be classified perfectly up front, so we give it a budget: retry on later polls, but count the attempts. After log_regroup_max_attempts (3) it's dead-lettered — abandoned_at is stamped, it drops out of the backlog, and a CRITICAL fires. This is the circuit-breaker that stops a poison window (a permanently-dead block underneath it) from burning the 120 s timeout on every poll forever. Parking is reversible: POST /logs/regroup/reset-abandoned re-arms it once the cause is fixed.

Idempotency & content-hash dedup

Safe repeats are the backbone of resilience

Entries dedup by sha256(content) and transactions use deterministic ids, so re-fetching or re-stitching never duplicates and always converges. That's what makes "skip now, pick it up later" safe.

Graceful degradation

Partial-but-honest beats a crash

When a bad block is unavoidable on a read, return what you can (the transaction list) with an explicit notice, instead of a blank 500. The user keeps working and understands what happened.

Observability · loud signals

Never degrade silently

Every skip emits a CRITICAL log and bumps a counter (io_skipped). A system that quietly limps hides a failing disk until it dies hard; make the degradation visible so a human can act.

Source-of-truth separation

Know what's authoritative vs derived

The real data lives upstream in the Windows log files; the database is a derived, re-ingestable copy. Because of that, losing a block is tolerable and recovery is "re-fetch." Identifying which data is the source of truth is what makes a data-loss decision safe.

Honest limits

Software routes around hardware; it doesn't heal it

All of the above keeps the app running and observable on a failing disk — it cannot recover rows on a dead sector or stop the disk degrading. Resilience is a stopgap; pair it with a routine backup so a full failure is survivable.

F. Where it lives, in code

io_errors.py
new — is_disk_io_error() / disk_io_detail(): one place that recognises the "could not read block … Input/output error" signature and extracts the block locator.
parse_insert.py
range from INSERT … RETURNING timestamp (no old-data scan); the ingest transaction relaxes statement_timeout to a finite worker cap (SET LOCAL … = 120000 ms — finite, never 0/disabled, so a slow insert can't hang forever) + smaller batches so slow inserts finish; disk faults (a dead block OR a slow-disk timeout) are logged loudly and the job labelled "disk fault".
remote_fetcher.py
per-file catch → skip + io_skipped counter + continue the poll; surfaced in the fetch stats.
derive_transactions.py
Stage-2 stitch relaxes statement_timeout per window (same 120 s cap), leaves a failed window pending while other windows still commit, and dead-letters it after log_regroup_max_attempts failures (attempts/abandoned_at); reset_abandoned_windows() re-arms parked windows.
logs.py
feed read returns the transaction list + a notice instead of a 500 when a page's entries are on a bad block; GET /regroup/status reports abandoned_windows and POST /regroup/reset-abandoned re-arms them.
tests
error-classification (direct + chained), the RETURNING insert the pending-range relies on, the finite-timeout guard, and the dead-letter + re-arm lifecycle — 91/91 backend tests green.

Remember

This keeps the system alive and observable on a disk with bad sectors. It does not heal the disk or recover dead-sector rows — keep a routine pg_dump, and treat the failing disk as living on borrowed time.
