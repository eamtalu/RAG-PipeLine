MNP log ingestion · design note

Fetch and parse, decoupled

Today one poll tick downloads bytes, parses them, and inserts rows in a single unbroken sequence. This splits that in two, using one new table as the durable handoff — without touching log_entries, jobs, or Stage 2.

2026-08-02 Status: proposed New tables: 1 Table rewrites: 0

The shape of the change

One await is the whole problem

Inside the byte-read loop, _pull_range awaits parse-and-insert before reading the next window. Everything downstream of that await happens while the SSH connection and the per-host lock are still held.

The pattern already exists one stage later

Stage 1 already writes a durable work ticket for Stage 2 — a log_regroup_pending row committed in the same transaction as the entries themselves (parse_insert.py:177-179). That is why Stage 2 can fail completely and still be retried. The fetch → Stage 1 hop is the only one missing it.

— in-flight await,
nothing written down →
Stage 1parse + insert entries
— log_regroup_pending row,
durable and retried →
Stage 2stitch transactions

Adding log_source_objects makes the first hop look like the second.

Pointer movement

Where the bookmark ends up

The bookmark is log_ssh_file_checkpoints.last_offset — how many bytes of a remote file have been consumed. Every scenario below is the same remote file, read left to right.

■ ingested    ■ downloaded, not yet parsed    ■ not yet read

Happy path

Bookmark advances
  1. Fetcher downloads bytes 5000–9000 and writes them to ./uploads.
  2. One transaction: insert the row as pending, and move the bookmark 5000 → 9000.
  3. Host lock released. The fetcher moves to the next file immediately.
  4. Parse worker leases the row, reads the local file, inserts log_entries, writes log_regroup_pending.
  5. Row marked ingested. The file is now provably redundant and can be deleted.
ingested · 0–9000 not yet written by the server
last_offset = 9000

Net effect: the bookmark moved once, atomically, and everything it skipped past is permanently in the database. The next poll reads only what the server has written since.

Crash after download, before the commit

Bookmark stays put
  1. Fetcher downloads 5000–9000 and writes the file.
  2. Process is killed before the transaction commits.
  3. No row exists. The bookmark was never moved.
  4. An orphan file is left in ./uploads — the only cost.
ingested · 0–5000 re-read on the next poll
last_offset = 5000 (unchanged)

Net effect: the next poll re-downloads 5000–9000 and starts over. Identical to today's behaviour. Nothing is lost.

Parse worker dies mid-parse

Bookmark already moved — safely
  1. The transaction committed, so the bookmark is at 9000 and the row exists.
  2. The worker leases the row and crashes partway through inserting.
  3. The insert transaction rolls back — no half-ingested entries (parse_insert.py:195).
  4. The lease expires. Another worker picks the same row up.
  5. It re-reads the local file. No network transfer.
ingested · 0–5000 queued · 5000–9000 not yet read
last_offset = 9000

Why moving the bookmark early is safe here: the bookmark is no longer the only record of what needs doing. The row is, and it survives the crash. That is the entire point of committing both together.

Parsing fails repeatedly — bad sector, corrupt bytes

Dead-lettered, nothing lost
  1. Each attempt increments attempts and records last_error.
  2. available_at backs the retry off rather than hammering the disk.
  3. At max_attempts the row becomes abandoned with a CRITICAL log.
  4. The downloaded bytes stay on disk. The row records exactly which file, offsets, and fingerprint.
  5. Fixing the cause and re-arming the row replays it — no re-fetch needed.
ingested · 0–5000 abandoned · 5000–9000 still fetched normally
last_offset = 9000

Compare with today: a poisoned range currently blocks the bookmark forever, so every poll re-downloads the same failing bytes indefinitely, leaving another dead jobs row and another file copy each time. Here it is isolated, and everything after it keeps flowing.

The design this avoids

Why it has to be one transaction

The obvious version — move the bookmark once the download succeeds, then hand off — loses data. If the handoff row is never written, or is written in a separate transaction that fails, the bookmark has already skipped past those bytes. No future poll will ever read them again.

DesignBookmark moves when…Crash between the two steps
Todayparse + insert succeededsafe re-download, retry
Naive splitdownload succeededdata lost silently, forever
Proposeddownload succeeded and row committedsafe atomic, both or neither

There is a second consequence worth planning for. Today the await gives free backpressure: the fetcher physically cannot outrun the database. Remove it and it will happily download faster than the parser drains, filling ./uploads. The fetcher needs a queue-depth guard.

Rollout

Six steps, reversible by config

Steps 2 and 3 sit behind one settings flag. With the flag off, the current inline path runs completely unchanged — so rolling back is flipping a boolean, not reverting a migration.

#StepBehaviour change
1Migration adds the table and its three indexesnone nothing reads it
2Parse worker, flag-gated, default offnone queue is empty
3Fetcher writes to the queue, same flaggated flag off = today exactly
4Fix the reporting that can no longer be accuratevisible API + frontend
5Purge and full-wipe paths clear rows and filescloses orphan risk
6Delete files once their row is ingestedreclaims disk

Step 6 is worth more than it looks

LocalStorage.delete exists but has no caller anywhere in the log path. Every byte ever fetched over SSH is still sitting in ./uploads, duplicating what is already in Postgres, because nothing has ever tracked whether a file was successfully ingested. The ingested status makes that provable for the first time — and this is a disk that is already failing.
