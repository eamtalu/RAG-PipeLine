Feed the analyst sees the transaction

Why the bookmark and the ticket must commit together

The file bookmark (log_ssh_file_checkpoints.last_offset) is a promise that everything behind it is handled. Move it without the ticket and those bytes are skipped forever, with nothing reporting it. Write the ticket without moving it and the next poll re-downloads them.

Committing both in one transaction removes the window entirely: a crash before COMMIT simply leaves the previous state, and the next poll re-fetches — which is exactly what happens today.

What actually changed

Before and after

Before

One poll tick did everything: download → parse → insert → stitch, holding the SSH connection and server lock throughout.
A slow database blocked network fetches for that whole server, for every tenant.
Crash mid-parse → file orphaned, nothing recorded it needed work. Recovery was accidental.
A bad file retried every poll forever, writing another ./uploads copy and another jobs row each time.
A non-disk error instead disabled the whole server after 10 tries.
Five modules had to remember to call Stage 2 — including the SFTP transport and a directory watcher.
Stage 2 retried on every tick with no delay: all 3 attempts gone in seconds, before a transient fault could clear.
Nothing ever deleted files from ./uploads.

After

Three independent loops, each on its own clock, joined by two durable queues.
The lock is released as soon as the bytes are down.
The ticket survives any crash; the work is picked up again, reading the local file.
3 attempts with growing delays, then dead-lettered and flagged — and hopeless failures give up on the first try.
A bad file no longer touches the source breaker; per-file and per-server failures are separate concerns.
One consumer drains each queue. Producers only write tickets.
30s / 60s / 120s with jitter, so the retries can actually succeed.
An ingested row proves the file is redundant, so it can finally be deleted.

Failure handling

One retry policy, both queues

Backoff and failure classification live in one module (app/services/queueing/retry_policy.py) so the same failure behaves the same way whichever queue it lands in. A test asserts neither worker reimplements it.

FailureExamplesWhat happens
Transientbad sector, statement timeout, dropped connectionBack off (30s / 60s / 120s + jitter) and retry until the budget is spent
Permanentcorrupt bytes, missing file, unparseable contentAbandon on the first attempt — retrying cannot help, and 3 tries just triple the log noise and re-read a bad disk area
Unknownanything unrecognisedTreated as transient. The budget bounds it either way, so a couple of retries beats discarding work that might have succeeded
pending ──claim──▸ leased ──success──▸ ingested ──sweep──▸ (file deleted) ▲ │ │ ├─ transient ──────▸ pending, attempts+1, available_at = now + backoff │ ├─ permanent ──────▸ abandoned (CRITICAL alert, budget untouched) │ ├─ budget spent ───▸ abandoned (CRITICAL alert) │ └─ lease expired ──▸ pending, attempts+1 (worker crashed) │ └────────── POST /logs/ingest-queue/reset-abandoned ──────────┘

Poison isolation

FOR UPDATE SKIP LOCKED means one stuck row never blocks the queue behind it. That is precisely the failure the old design had at source level, where one unparseable file could eventually disable an entire server.

One frontend change is required

useRemoteFetch.ts documents the old guarantee in a comment: "the run FINALIZES INTERNALLY … never call finalize after a fetch." That is now false, so reloading the feed the instant a run completes shows data that has not been stitched yet.

The fix is ~10 lines: poll getRegroupStatus() until up_to_date, then reload. Full brief in docs/plan/2026-08-05_frontend-stitch-timing-change.md.
