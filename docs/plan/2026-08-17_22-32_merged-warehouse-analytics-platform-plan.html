Words used here

Every term that could be mistaken for jargon. Terms marked with a dotted underline in the body are defined here.

projection

A table built from other data rather than written directly. log_transactions is one: it is assembled from raw log lines and can be rebuilt.

append-only

Rows are only ever added, never changed or removed. log_entries is append-only. log_transactions is not.

sealed / unsealed

Sealed means the system considers a record final. Unsealed means it may still be rebuilt.

ledger / contribution

One row per record saying what it added to the totals. Keeping it lets a record be undone precisely.

version hash / fingerprint

A short signature of the values that affect a total. Same fingerprint means nothing changed, so no work is needed.

delta application

Adjust a total by the difference: subtract the old contribution, add the new one.

ticket / dirty window

A durable note saying "records in this time range changed, go and recheck them".

idempotent

Running it twice has the same effect as running it once. What makes retries safe.

at-least-once

Work may be delivered more than once but never lost. Combined with idempotence, the effect is exactly once.

reconciliation

Recount from scratch and compare against the running totals, to prove they have not drifted.

grain

How coarse a saved total is: hourly, daily, weekly, monthly. Coarser means fewer rows to read.

additive

Can be summed across periods. Counts and sums are. Averages, percentiles and distinct counts are not.

cursor / bookmark

A stored marker saying how far a reader has got, so old data is not deleted before it is read.

partition

One physical slice of a big table, here one per day. Old slices are dropped whole, which is cheap.

event time vs write time

When the pick happened, versus when the row was written. Here they differ by hours.

advisory lock

A named lock two jobs can share to avoid working on the same thing at once.

point-in-time correctness

Being able to rebuild exactly the data a model was trained on, months later.

merge / split

When rebuilt, two records may combine into one, or one may divide into two. Ids appear and disappear.

backfill

Computing history for something newly defined, rather than only going forward from now.

Why the design looks unusual

log_transactions is not an append-only table and not a time series. It is a mutable projection: each record is stitched from roughly 15 raw log lines, and when a late line arrives the row is deleted and rebuilt, possibly with different values.

98.7%of rows written more than 5 min after their own log lines
1.7 haverage gap for sealed rows
5.4 hworst observed gap
0.6%built promptly, within 60 s

So rebuilding is the norm, and a row is not final until hours after the event. Two conclusions follow, and they rule out the two obvious designs.

  • Simply adding numbers up is wrong. A rebuilt row would be counted twice, producing plausible-looking wrong totals with no error.
  • Waiting for rows to settle is also wrong. Sealing is measured against the newest log timestamp, not the clock (derive_transactions.py:535-538), so the wait has no bound and stops entirely whenever ingestion pauses.

Consequence for implementation

The version hash on each contribution is load-bearing, not an optimisation. At a 98.7% rebuild rate almost every recheck must be absorbed as a no-op by a matching fingerprint, or the system produces a constant stream of pointless aggregate writes.

Verified ground truth

Read from the live server and from code. Do not re-derive.

Volume and shape

72,682 transactions. ~1,100,516 raw log entries. 1,474,393 parsed M3 records inside log_entries.fields. Peak 68 transactions/minute, 13 picks/minute.

Cardinality grows slowly

692 distinct items with consumption, 395 on the busiest day, against 25,008 in the item master. More picks does not mean more items.

Scan cost

~2.5 µs per row. 1.04 M rows took 2,541 ms. Planning cost tracks partition count, not data volume: 7 ms for one partition versus ~85 ms for 21.

Filter on method

Never transaction_type, which holds placeholders like xxxxxx. AddStockCountLine carries real quantities under a placeholder, so a type filter drops real data.

Quantity fields

QuantityPicked and ExpectedQuantity are 100% clean. QuantityToBePicked is 91% empty and Weight is 100% empty. Values are fractional, so NUMERIC throughout, never float.

Identity

A new record's id is uuid5 of an anchor line's hash. A rebuilt record inherits its id. Source uniqueness is (id, started_at), not unique on id alone. See the correction below.

Live checks, 2026-08-17

NULL started_at: 0. Duplicate ids: 0. NULL ended_at: 0. Unsealed at any moment: 1,638. Regroup tickets: 7,407 with 0 pending, 0 abandoned, 0 retries.

Real data loss, today

847 to 1,079 orphaned log lines belong to no record, all past the abandon window, from two files. Only 7 are pick-related.

Infrastructure limits

Stock PostgreSQL 16. No TimescaleDB, Citus, columnar, hll, tdigest or pg_partman. work_mem is 4 MB. Partitioning helper supports daily bounds only.

Frontend limits

No chart library, so charts are hand-built. next.config.mjs needs a rewrite entry or /api/v1/analytics/* returns 404.

Identity, re-verified 2026-08-18

An earlier version of this plan had this backwards

It said "1.3% are exposed to id change on backfill". Backfill is the one path that is protected. The 1.3% figure is the measurement that motivated the fix, not a live exposure.

A new group's id is uuid5 of its anchor line's hash, the anchor being the REQUEST line if there is one and the earliest line otherwise. A rebuilt group inherits its id from whichever record owned the plurality of its lines, via continuity.assign(...) in _resolve_ids.

But that inheritance is wired into only one of the three rebuild paths. Traced through every call site:

PathWhat it deletesInherits ids?Result
regroup_window
:858, :895		 all records in the padded range, sealed includedyesid preserved
regroup_incremental
:780, :801		 unsealed only, no time boundnoid recomputed, so it can change

:677, :698		 everythingnoid recomputed, so it can change

So stability holds for backfill and repair, which is the case the 1.3% was about. It does not hold on the live path, where an unsealed record gaining a late REQUEST line will change id.

A documentation bug worth reporting upstream

The docstring at derive_transactions.py:575-576 states "Only regroup_window can supply one, because only it frees transactions." That is inaccurate: regroup_incremental:780 and regroup_all:677 both delete records. The comment would lead the next reader to believe the live path is protected when it is not.

Impact on this design: none, and that is the point

The range diff reverses a vanished id and applies a new one, so an id change is handled exactly like a merge or split. This is further evidence that the range diff is mandatory and a per-record update would be wrong. It does mean the ledger sees more identity churn than reading continuity.py alone suggests.

Adopted unchanged

From the 2026-08-11 plan, correct and preserved: the contribution ledger with delta application; the transactional ticket; NUMERIC(38, 9) quantities; refusing Flink and Kafka with measurements rather than opinion; rejecting a write-time cursor, database triggers, in-memory totals, per-request aggregate queries and WebSocket-first delivery; revision polling before server-sent events; read-only web workers with the loop in the singleton worker process; deploying schema first, then tickets with the worker disabled, then one tenant; freshness shown beside business numbers; and query plan evidence before fixing index order.

The eleven fixes

Each is a defect found in the earlier plan by code reading and live measurement. Red is blocking, amber serious, blue smaller.

F1

Ticket bounds must come from the delete, not the new lines

defect
regroup_window has explicit bounds, but the live path regroup_incremental deletes WHERE sealed IS FALSE with no time predicate. Bounds taken from incoming lines would miss an older unsealed row caught in the same delete, which then drifts permanently. This path runs every ~70 seconds.

fix
Every publisher computes bounds from the set actually freed. The unsealed ids are already selected before the delete, so take min and max started_at over that same set and publish it padded. Empty set means no ticket.

invariant
No record may be deleted by any path without a committed ticket whose range contains its started_at.

F2

Reconciliation must also check completeness against log_entries

defect
The proof of correctness recomputes from log_transactions. Both sides read the same projection, which is currently missing ~1,000 orphaned lines, so reconciliation passes while under-counting.

fix
Two independent scheduled checks. First, totals against a recount. Second, a count of log_entries rows past the abandon window with no row in log_entry_assignment, grouped by source file and program. Surface both in the state row and on the dashboard.

act now
Run a scoped regroup over 2026-08-15 to 2026-08-17 for the two named files, and find the cause before assuming a regroup fixes it, because whatever caused it will recur.

F3

Ledger identity must mirror the source constraint

defect
Keying contributions on the record id alone. Source uniqueness is (id, started_at), and two rows can share an id in different partitions "silently and undetectably". A ledger keyed on id alone would collapse them and under-count.

fix
Key on (customer_code, source_transaction_id, source_started_at). Zero duplicate pairs exist today; the extra column costs nothing and removes the failure mode.

F4

Freshness needs two numbers, not one

defect
The 5-second target measures how far analytics lags the projection. But records are not final for 1.7 h on average. The screen could truthfully say "updated 2 seconds ago" about a number still due to move, which manufactures false confidence.

fix
Copy freshness: seconds between the analytics watermark and the source watermark. Settledness: the share of contributing records still unsealed, and the age of the oldest. A window with unsealed contributors reads as provisional, not stale, because those mean different things to an operator.

F5

The status endpoint must read exactly one row

defect
The browser polls status every 2 seconds per tab across four web workers, and the response includes counts over other tables. The cheapest request becomes the most frequent expensive one.

fix
The worker writes every status field into the single warehouse_analytics_state row each cycle. The endpoint is one key read plus an ETag. A test asserts it issues exactly one query.

F6

The retention bookmark must publish a write-time position

defect
Retention gating uses a cursor measured in write time, but the worker is driven by event-time ranges and has no natural write-time position. Unresolved, it either publishes nonsense or gates nothing, and the second loses data during the backlog that caused it.

fix
Track the maximum created_at seen among fully processed rows and publish the minimum across tenants under analytics:warehouse-v1. A ticket is only acknowledged once its whole range is diffed, so every row inside it has been read.

watch
A deferred team change would switch the delete-and-reinsert to an UPDATE. Then created_at stops moving and this fix breaks silently. Keep the cursor field a single named constant so the switch to updated_at is one edit. That change would also collapse the 98.7% figure this plan is sized against.

F7

Copy the existing ticket table; do not share it

resolved
log_regroup_pending already has exactly the needed columns and is healthy in production. Copy its shape, but analytics gets its own table, for two reasons.

  1. consumed_at is a single-consumer field. A second consumer stamping it means whichever runs second finds the window closed and skips work it never did.
  2. The existing tickets are written in Stage 1, per ingested file, so they describe ingest ranges and only ever drive regroup_window. They never describe the live path.

F8

Zero-quantity picks are attempts, not consumption

defect
9.2% of pick confirmations record zero units and still say success, typically an empty location. Counting them as picks inflates productivity by about a tenth.

fix
Three counters, all stored in every rollup: quantity (sum of units), pick_count (confirmations above zero), attempt_count (all confirmations). The zero-pick rate derives from the last two and is a first-class metric, because it names specific empty locations and replaces the fill rate this data cannot support.

F9

Add daily and monthly grains; derive weekly

defect
Hourly and lifetime totals only. A month-to-date question means summing about 1.08 M hourly rows, roughly 2.7 seconds and growing.

fix
See Grains and additivity below.

F10

Keep contribution history, or machine learning is impossible later

defect
The ledger keeps only the latest value per record, so a rebuild overwrites the previous one. A training set built from it is not reproducible: the same query returns different data next week, no experiment can be replayed, and nobody can explain an old forecast. Discarded versions cannot be recovered.

fix
Two tables. warehouse_consumption_contributions holds the latest value and serves the delta computation. warehouse_consumption_contribution_history is append-only, one row per version with its revision, retained longer than raw data. Training sets pin a revision and become reproducible exactly.

F11

Load testing needs a synthetic tenant

defect
The exit criterion requires holding at 100× the measured rate, roughly 78,000 records an hour, with no way described to generate that without polluting real data.

fix
A dedicated synthetic-load tenant whose generator produces realistic lines and drives Stage 2 normally, so tickets and rebuilds are genuinely exercised. Excluded from every production read path and from alerting. It also produces the defect fixtures, so correctness and load share one harness.

Additional hardening

Ten further findings the headline eleven do not cover.

#ItemWhy
A1Quarantine must never halt a tenantHalting on one bad row freezes every metric until a human intervenes. The codebase already chose the opposite: "the survivable failure, made loud".
A2Do not reuse the stitcher's lock keyThe stitcher holds hashtext(customer_code). Sharing it means a slow analytics run stalls log stitching. Analytics lagging is survivable; ingestion stopping is not.
A3Ticket table provably constraint-freeIt is written inside the ingestion transaction, so any failed insert fails ingestion. No foreign key, no unique constraint a retry could violate, no trigger.
A4Routine reconciliation must be windowedFull recount grows with all retained history, becoming a multi-hour job that quietly stops being run.
A5One authoritative revisionTwo revision counters exist. The tenant one governs cache validation and must bump in the same commit, or a valid cache tag returns stale data.
A6Normalise the missing-warehouse value onceMapping null to a sentinel in two code paths lets one item's total silently split across two keys.
A7Every source read carries the window predicateIncluding include_null=True, because a range test is false for null and null started_at is documented as possible.
A8Align the worker cadencePolling every second against 68 records/minute mostly finds nothing. Tickets are durable, so latency is bounded by ticket availability.
A9SET LOCAL work_mem = '64MB'The global 4 MB spills grouping to disk over thousands of items, and the global value is shared with ingestion.

Metric registry

Decided 2026-08-18: this is the centre of the design

The user chooses what is measured and how it is sliced, from the interface, and the measure list is not fixed now. So nothing about dimensions or measures may be hardcoded into a rollup schema.

The consequence that cannot be deferred

If measures are chosen later, the fact row must capture every potentially useful field now. Raw data is dropped at 60 days, so a measure invented next year can only be backfilled across history if its fields were already being written. A consumption-only ledger would make "average duration by device" permanently impossible beyond 60 days.

So the ledger widens into a full fact row:

GroupFields
Identitysource_transaction_id, source_started_at, source_version_hash, revision
Timeevent_time, business_date (tenant-local), duration_ms
Operationmethod (49 values), transaction_name (22), transaction_type, status
Subjectitem_number, lot_number, order_number, delivery_number
Placewarehouse, warehouse_id, from_location, to_location
Actoruser_name, device_id, device_name
Measuresquantity where present, attempt and pick classification, plus a typed slot per registered measure

Wider than the earlier plan specified, deliberately. The fact table is the only durable record, so anything not written here is lost at 60 days.

Dimensions confirmed

Aggregate by both method (49 values, API level) and transaction_name (22 values, the operator's screen). Both are low cardinality, so together they stay under roughly 1,700 hourly rows per day.

Only 2 of the 49 methods carry quantities

ConfirmPickLine (14,654 rows) and ReportCount (9,076). For the other 47 the meaningful measures are volume, duration, status and actor. The interface must not offer a quantity measure for a method that has none.

How a user-defined metric works

1
The user picks a dimension set, a measure, a filter and a grain in the interface.
2
That writes a definition row: identifier, dimensions, measure, filter, grains, and a draft/active/inactive lifecycle.
3
The worker begins maintaining its rollups on the next cycle.
4
A backfill populates its history from the fact table, which is only possible because the fact row is wide and retained. This is the payoff for the widening above.

Rollups are stored generically: a definition identifier, a fixed number of dimension slots and additive measure slots, rather than a bespoke table per metric. Adding a metric is a row plus a backfill, never a migration.

The honest limit

Fully arbitrary slicing over years cannot be pre-aggregated, because the combinations explode. Registered definitions are fast at any range. Genuinely ad-hoc exploration falls back to a bounded scan of the fact table, and the interface must show that distinction rather than silently running a slow query.

Also: a newly defined metric has no history until its backfill runs. That is a fact of the design, not a bug, and it should be visible in the interface.

Selection

Toggleable. A chosen set of types renders either as one series per type or as one combined total. Both are valid from the same rollup because counts and sums are additive. Percentiles across a selection need merged histograms, never averaged percentiles.

Additivity is a schema rule, not advice

A rollup stores components, never finished answers. Averaging twelve monthly averages is not the yearly average.

No hll or tdigest is available, so distinct counts have no approximation to fall back on. They are computed per period from the ledger, which is cheap because the ledger and the monthly grain share a partition boundary.

ML and agentic pipeline

Now, cannot be added later

The append-only contribution history from F10, with its own retention and a revision that training sets pin.

Cheap and early

Analytics tools added to the existing Claude agent at POST /api/v1/logs/debug/ask. Tenant is injected server-side and never model-exposed. The registry is what makes those tools generic rather than one per metric.

Deferred, seam ready

Forecasting and anomaly detection. No data-science dependency is installed. Anomaly alerts reuse the existing notification rules, channels and delivery tracking.

Unrelated live bugs

A worker retries CREATE EXTENSION vector forever on a server without pgvector, every ~4 s on both processes. And hybrid search raises TypeError on the default backend.

Read API and frontend

Endpoints in app/api/v1/analytics.py, registered in the existing router, every one tenant-scoped. Keyset pagination with default and hard maximum limits, no default row count, cache tags honouring conditional requests, and 202 Accepted for backfill and reconcile.

Added by this merge: status is a single-row read (F5); responses carry both freshness numbers (F4) and the completeness count (F2); grain selection happens server-side in one method so no caller can scan a fine grain over a wide window (F9).

Three frontend facts to design around. There is no chart library and adding one would be the repo's first in two years, so hand-rolled inline SVG matches convention. Styling is one global CSS file with tokens and an nx- prefix for new work, and the notifications activity tab is the only existing table-plus-tiles-plus-polling page to copy. And next.config.mjs needs a rewrite entry or every request 404s.

Phase 0Contract and fixtures. The consumption definition with the three counters. Verification

Grouped by consequence. Every item is a failure that produces a plausible wrong number rather than an error.

Correctness of the total

  1. Reconciliation: ledger totals equal a direct recount for the window.
  2. Completeness: lines past the abandon window with no assignment, by file and program. Currently non-zero, so this test starts red and that is correct.
  3. Restatement: rebuild an already-folded window and assert totals unchanged; change a quantity and assert the old contribution reverses exactly once.
  4. Merge and split: a merged record's vanished id reverses, a split's new id applies. A per-record update passes test 3 and fails this one.
  5. Ticket coverage: rebuild an old unsealed row via the live path and assert a committed ticket contains it.
  6. Identity: the ledger key includes source_started_at, and two rows sharing an id produce two receipts.
  7. Idempotence: the same fold twice leaves values unchanged.
  8. Crash safety: kill the worker mid-batch; no gap, no duplicate.

Data that cannot be recovered

  1. Retention independence: drop a 61-day-old raw partition; ledger, history and grains survive.
  2. Cursor gating: the position blocks retention while behind; a stalled worker is logged critical then stops blocking.
  3. Reproducibility: build a training set at a revision, restate a contribution, rebuild at the same revision, assert identical output.
  4. Rebuildability: delete a grain entirely and rebuild it from the ledger to identical values.

Traps specific to this data

  1. Attempts versus picks: zeros excluded from pick count, included in attempts and the zero-pick rate.
  2. Additivity: monthly-grain metrics equal ledger-computed ones, including distinct count, p95 and average.
  3. Top-N is not composable.
  4. Local business date at 00:30 during BST lands on the right local day.
  5. Numeric fidelity end to end; comparisons numeric, never string.
  6. Placeholder rejection: quarantined with a reason, never dropped silently.

Registry and user-defined metrics

  1. Fact-row completeness: every listed field is populated wherever the source has it. This guards the one irreversible schema decision.
  2. A newly defined metric backfills correctly: define one for a combination never registered before, backfill, and assert it equals a direct aggregate. This proves user-defined metrics are real rather than forward-only.
  3. Selection is additive both ways, and percentiles come from merged histograms.
  4. Quantity measures are refused where the field does not exist, since 47 of 49 methods have none.
  5. ISO week boundaries during BST.

Performance and end to end

  1. Status is one query. Queries are prepared, worth ~100 ms each.
  2. A 12-month request resolves to monthly, never daily. Grain reads plan as index-only scans, with query-plan proof.
  3. Load: synthetic tenant at 100× the measured rate, worker lag inside target.
  4. In the real interface: a live pick updates within target; a window with unsealed contributors reads as provisional; empty and loading states, fractional formatting, light and dark all checked.
