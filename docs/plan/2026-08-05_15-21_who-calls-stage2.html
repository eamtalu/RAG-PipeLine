Who calls Stage 2?

Stage 1 never calls Stage 2. It only leaves a note saying "this time range needs stitching". Something else has to come along and act on that note. This is about who, and when.

Why two processes

Under gunicorn -w 4 the startup hook runs in every worker. Left alone that would start 4 pollers, 4 of everything, all fighting over the same rows. One environment variable decides which process owns the loops.

Where the parse worker fits

It starts from the same place — start_background_tasks() — as a sibling of the poller, not underneath it. That is why it keeps running after a poll ends.

Four independent safety limits

Singleton lock (one process) → one task per customer → semaphore of 8 → one lock per server. Each solves a different problem, and they stack.

Proposed next — not built

Give Stage 2 the same two improvements

Stage 2 keeps working exactly as it always has. These are its two pre-existing rough edges, which the new queue already solves.

1. Wait between retries

Stage 2 retries a failing window on the very next poll, with no pause. All three attempts are gone within seconds — before a temporary problem has any chance to clear.

Stage 2 today
try 1 try 2 gave up
New queue
try 1 try 2 gave up
0s30s60s90s

Spreading them out is not politeness to the disk. It is what makes the retries actually useful — a busy disk or a held lock usually clears in that time.

2. Stop wasting tries on hopeless failures

Stage 2 today

Every failure looks the same to it. A window with corrupt bytes is read, fails, read again, fails, read a third time, fails.

Two of those three reads were guaranteed to fail before it started — on a disk that is already struggling.

New queue

Checks why it failed. Disk hiccup or timeout → might work later, so use the retries. Corrupt bytes or missing file → can never work, so stop now and flag it.

Add available_at <= now() to the open-window query1 line

Why it is not in this change

You asked for proof of no regression. That is provable right now because derive_transactions.py is byte-for-byte untouched. Tangling a Stage 2 edit into the same change would make any future problem much harder to attribute.
