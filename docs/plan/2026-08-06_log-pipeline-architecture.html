01

The shape: three queues, four workers, nothing calls anything directly

Every stage of this pipeline is separated from the next by a database table used as a work queue. No stage calls the next one. A stage writes a row saying "this needs doing" and commits; a worker on its own clock picks it up.

That single decision is what makes the system survivable. A crash between stages loses nothing, because the ticket is already committed. A slow database cannot block an SSH download. And a new ingestion path cannot forget to trigger the next stage, because it does not trigger anything — it just writes its ticket.

Queue 1 log_source_objects

“These bytes were downloaded and still need parsing.” Written in the same transaction that advances the SSH read checkpoint.

Queue 2 log_regroup_pending

“Entries landed in this time window; it needs re-stitching.” Written by the parser as it inserts.

Three independent paths put log bytes into the system. All three end the same way: bytes saved to object storage, and a ticket row committed.

The fetch ticket, and the one thing that makes it safe

The SSH fetcher tracks how far it has read each remote file in log_ssh_file_checkpoints. Writing the ticket and advancing that checkpoint happen in one transaction, in _queue_and_checkpoint().

If the checkpoint advanced alone

Those bytes are marked "read" but no ticket exists. Nothing ever parses them, and the fetcher will never look at them again. Silent, permanent data loss.

If the ticket were written alone

The checkpoint has not moved, so the next poll downloads the same bytes again — forever. An infinite re-download loop.

Both are avoided by refusing to do one without the other. This is the transactional outbox pattern: the work item and the state change it depends on are committed together or not at all.

fetch_now remote_fetcher.py Takes a per-host advisory lock so two pollers never fight over one server.
for each rotated / grown file
_stage_range remote_fetcher.py SFTP-reads [start_offset, end_offset) and saves the bytes to storage.
one transaction
_queue_and_checkpoint remote_fetcher.py INSERT the log_source_objects ticket and UPDATE the checkpoint, then COMMIT. Either both land or neither does.

Backpressure

_queue_backlog_exceeded() pauses fetching when too many tickets are unparsed. Before the split, the await on parsing provided that throttle for free; once the two were decoupled the fetcher could otherwise outrun the parser and fill the disk with downloaded bytes nobody had processed yet.

03

Stage 1, part two: the parse worker turns tickets into raw entries

workers/log_parse_worker.py — one loop, roughly every two seconds. It is the only consumer of queue 1, and the only writer of log_entries.

claim_one log_parse_worker.py:68 Takes the oldest due ticket with FOR UPDATE SKIP LOCKED and marks it leased. SKIP LOCKED means a stuck row never blocks the rest of the queue, and several workers could run safely.
process_claimed log_parse_worker.py:221 Loads the stored bytes, creates a Job row, and runs the parser.
run_log_parse_insert pipeline/parse_insert.py Parses each line, attaches the customer's timezone to turn local wall-clock into a true UTC instant, then bulk-inserts with ON CONFLICT (customer_code, entry_hash, timestamp) DO NOTHING.
the same function writes the next ticket
INSERT log_regroup_pending parse_insert.py:189 “Entries landed between range_start and range_end; that window needs stitching.” The range comes from the RETURNING clause of the insert — only rows actually written, never a scan of old data.

Deduplication is content-based

entry_hash = sha256(raw_body) — the whole raw line, including its millisecond timestamp. Re-ingest the same file and every line collides with the row already stored, so it is skipped. This is what makes the whole pipeline safe to replay.

When a ticket fails

Every ticket carries its own retry budget, so one bad file cannot damage anything else:

  • Transient (disk I/O error, timeout, connection reset) → back off with exponential delay + jitter, retry until the budget runs out.
  • Permanent (undecodable bytes, unparseable content, missing file) → abandon on the first failure. Retrying cannot help, and three attempts would just triple the log noise.
  • Budget exhausted → status abandoned, logged CRITICAL. It stops being retried and waits for a human. POST /logs/ingest-queue/reset-abandoned re-arms it.
  • Worker crashed mid-parse → the lease expires and reclaim_expired_leases() hands the ticket back to the queue.

Before this existed, a single unreadable file was retried on every poll forever, writing another copy of the bytes and another jobs row each time — on a disk that was already failing.

04

Stage 2: a separate worker stitches entries into transactions

workers/log_stitch_worker.py — one loop, roughly every second. It owns queue 2 completely. Nothing else invokes Stage 2.

This is the part that changed most

Stage 2 used to be called directly by whoever had just ingested something — the SSH fetcher at the end of a poll, the watcher after a file, the upload endpoint. Three call sites, and every new ingestion path had to remember to add a fourth. Forgetting meant data sat unstitched with nothing reporting it.

Now there is exactly one consumer, on its own clock, and producers only write tickets.

customers_with_due_work log_stitch_worker.py:59 Which tenants have an open ticket that is past its retry backoff. An indexed read of the small queue table — never a scan of the 60k-row entry table.
per tenant
finalize_pending pipeline/derive_transactions.py Merges that tenant's open windows into disjoint spans and processes each, splitting anything too large so one huge backfill cannot become a single giant transaction.
regroup_window derive_transactions.py The actual rebuild for one time range. Deletes the transactions anchored in the window, re-reads the now-unassigned entries, and rebuilds — all in one transaction.
_group → _persist derive_transactions.py Runs the REQUEST→RESPONSE state machine over the entries in stream order, then writes one log_transactions row per request cycle plus its log_entry_assignment rows.

Two ideas that make re-stitching safe

Deterministic IDs

A transaction's id is uuid5 of its anchor entry's content hash. Rebuild the same entries and you get the same id. So a regroup is idempotent, and a transaction id you saved or linked to stays valid forever.

Sealing

Once a transaction is old enough that nothing can still join it, it is marked sealed and never recomputed. Only the recent unsealed tail is reworked each cycle, so the per-cycle cost stays flat no matter how much history exists.

The padded window

A rebuild of [lo, hi] actually processes [lo − pad, hi + pad], where the pad is at least the seal window. A transaction can span at most that long, so any transaction a new entry could belong to is guaranteed to be inside the padded range — which is what makes the rebuild lossless at the boundaries instead of splitting a request from its response.

Dead-lettering, same pattern as queue 1

  • Each window has attempts, last_error, and an available_at backoff gate.
  • After 3 failures it is marked abandoned and logged CRITICAL — parked, not retried, so one poison window cannot burn the statement timeout every second.
  • Abandoned windows are excluded from the backlog, so they cannot pin the "not up to date" banner on forever.
  • POST /logs/regroup/reset-abandoned re-arms them.

The two clocks: event time and write time

Every row in this pipeline carries two timestamps, and they answer different questions. Almost every subtle bug in this system has been someone reaching for the wrong one, so it is worth learning once.

Which column is which

ClockColumnsWhat it drives
EVENT time
when the log line happened		 log_entries.timestamp partition key
log_transactions.started_at partition key
log_transactions.ended_at, .date
log_entry_assignment.entry_ts partition key
log_regroup_pending.range_start/end		 partitioning, retention, Stage 2's rebuild window, the seal window, grouping, display
WRITE time
when the row was stored		 log_transactions.created_at
notification_rules.cursor_at
consumer_cursors.position		 incremental reading, and nothing else

The rule, in one line each

  • “Where does this row live, and when did it happen?” → event time.
  • “Have I seen this row yet?” → write time.

Why a reader must never cursor on event time

Because event time arrives out of order, and not rarely - it is the normal case here. Every SSH poll considers ~98 rotated files (eSmartServerLog.txt.1 through .99); each one is older data landing later.

The one sharp edge: written is not committed

created_at is stamped when Python builds the row (log_transaction.py:132), not when Postgres commits it. So there is a window where a row exists carrying a timestamp the reader has already passed:

   build row (created_at = T) ─────────────────▶ commit at T+X
                                       ▲
             if X > the reader's lag, the cursor has already gone past T
             and that row is skipped permanently - dedupe cannot recover
             something that was never seen

The defence is that readers stay a fixed lag behind the present rather than reading up to now(). notification_cursor_lag_seconds = 60, and the setting's comment states the correctness condition plainly: it must exceed the longest Stage 2 transaction.

Measured on production: the longest single commit spans about 30 seconds of row-building, against a 60-second lag. Roughly 2x headroom - real, but not generous. If Stage 2 batches ever slow down (larger files, a slower disk), this is the margin that erodes first, and it erodes silently. It is a good thing to monitor rather than a thing to fix.

One place the two clocks are compared - worth verifying

consumer_cursors.blocks() decides whether retention may drop a day. It compares a write-time position against an event-time day boundary:

   day_end = <end of event-day D>        # EVENT time
   return min_position < day_end         # a created_at → WRITE time

Conservative in the ordinary direction. The case to check is a backfill landing in a partition older than the retention horizon: its created_at is now, so a reader sitting just behind it has not read it - yet the day boundary is 60 days old, so the comparison says the partition is droppable.

Recorded as unverified, not as a defect: it needs a reproduction before it means anything, and it is not reachable today (the first real partition drop is around 5 October 2026, and it requires backfilling data older than 60 days).

06

Storage: the three hot tables are cut into one file per day

All three high-volume tables are range-partitioned by UTC day. Deleting old data is now DROP TABLE on one day's partition — a file unlink — instead of DELETE + VACUUM, both of which read the entire table.

TablePartition keyWhy that column
log_entriestimestamp when the log line happened
log_transactionsstarted_at its first entry's timestamp
log_entry_assignmententry_ts a copy of its entry's timestamp, so it lands in the same day as the entry it describes

The partition worker

workers/log_partition_worker.py — hourly, both halves idempotent so a missed tick is harmless.

Create — the dangerous half

Keeps 14 days of partitions ahead of today. An insert into a day with no partition fails outright, so if creation stops, ingestion stops when the runway runs out. A failure logs CRITICAL and the remaining runway is reported every tick.

Drop — the irreversible half

Removes days past 60, behind three gates. A failure here reclaims no disk and simply retries, so it can never block creation.

The three gates before anything is dropped

  • Past retention — the day is older than 60 days.
  • No open stitch window overlaps it — dropping data Stage 2 has not finished with would destroy transactions that were about to be built.
  • Entries lag transactions by one day. A transaction starting at 23:58 owns entries into the next day. Dropping day N's entries while a day N−1 transaction still referenced them would leave it rendering half-empty, with nothing recording that its body used to exist. So transactions drop for day D, entries and assignments only for day D−1. One extra day of storage; the bound is exact, not a guess.

Observed in production, first tick

created=3 dropped=0, 14 day(s) of runway — and the 3 is the design working. The tick fell at 00:06 UTC, just after the UTC date rolled over, so the far edge of the runway moved by one day across all three tables. The worker reads the date in UTC, not the server's local Europe/London — a distinction that is invisible 23 hours out of 24, and that first tick landed inside the one hour where it matters.

Why the assignment table exists at all

Stage 2 used to write its result back onto log_entries as transaction_id and seq columns. Because those were indexed, every rewrite touched both the heap and the index — and the unsealed tail is regrouped repeatedly before it seals.

Measured in production: 105,838,123 row updates at 0.0% HOT on 1.9M rows. Roughly 55 rewrites per row. That was the write amplification and dead-tuple churn behind the outage, on a disk that could no longer complete a vacuum.

Moving the grouping into its own table made log_entries strictly insert-only. Five consecutive regroups of the same window now perform zero row updates.

No foreign keys between these three, on purpose

A foreign key makes the referenced table's partitions impossible to detach or drop — and retention is dropping partitions. So the references are soft, and every delete path clears assignments explicitly. Removing them also made the hottest write path about 4× faster (200k assignment inserts: 1,060 ms → 249 ms, two FK triggers × 200,000 calls each).

A structural consequence worth knowing

None of the three tables has a PRIMARY KEY any more. PostgreSQL requires a unique constraint on a partitioned table to contain every partition-key column, and silently forces primary-key columns to NOT NULL. All three partition keys are nullable — the parser genuinely emits entries whose timestamp will not parse — so a primary key would make those rows impossible to insert. Identity is a UNIQUE NULLS NOT DISTINCT instead, with the partition key present but never first.

The order is load-bearing and was measured: looking up by id alone takes 0.046 ms with (entry_id, entry_ts) and 10.8 ms with (entry_ts, entry_id) — a sequential scan, because the id is no longer seekable.

08

Why it looks like this: the failures each decision came from

Almost nothing here is a preference. Each piece exists because something specific broke.

DesignThe failure it came from
Fetch and parse split by a queue The SSH connection and the per-host lock were held while the database worked. A slow disk blocked network fetches for the whole server.
Per-ticket retry budget One unreadable file was retried every poll forever, each attempt writing another copy of the bytes and another jobs row — on a failing disk.
Per-file failures separated from per-server ones A single unparseable file used to increment the source's failure counter and would eventually disable the entire server, blocking every other file on it.
Stage 2 owned by one worker Three separate call sites had to remember to trigger stitching. Any new ingestion path that forgot left data silently unstitched.
Assignment table, entries append-only 105.8M updates at 0% HOT. Vacuum could not keep up; the heap reached 40 GB.
Daily partitions Retention meant DELETE + VACUUM, both full-table reads on a disk with bad sectors.
Every hot query carries a time bound PostgreSQL prunes partitions only from a predicate on the partition-key column. An unbounded query opens all ~130 of them.
Timezone changes refused once data exists The dedup key now includes the timestamp, which is derived using the customer's timezone. Change it and re-ingest, and the same line inserts a duplicate instead of being skipped.

One example of the bounding work, measured

_persist used to load every transaction id the tenant had ever had into a Python set — 109k rows per call, growing forever — purely to detect an id collision. It now asks only about the ids being written, inside a padded window. 25 partitions opened → 1, and memory now scales with the batch rather than with the tenant's history.

Operating it

The one endpoint that tells you if things are healthy

GET /api/v1/logs/regroup/status — polled by the AUTO-POLL card.

FieldMeansAct when
pending_windowsstitch backlogrising steadily
backing_off_windowswindows already failing and retrying above zero — this is the early warning
abandoned_windowsdead-lettered, waiting for a human above zero — always
partitions.days_aheaddays of partition runway below 3 — ingestion stops at 0
partitions.default_partition_rowsentries with no parsable timestamp growing — the parser is failing on some format
partitions.oldest_dayoldest day still stored not moving — retention has stopped

The partitions block is global, not per tenant. Partitions are cut by day, not by customer, so every log space shows the same values. It rides on this endpoint only because the card already polls it.

The knobs

SettingDefaultEffect
log_partition_retention_days60 how long data is kept. Dropping is permanent.
log_partition_precreate_days14 runway ahead — how long the worker can be dead before ingestion stops
log_partition_min_runway_days3 alarm threshold, shared by the worker and the status card
log_seal_window_seconds900 how long a transaction stays open to late entries
log_parse_max_attempts3 retry budget per ticket, both queues

Deploying a schema change here is not a rolling deploy

The dedup constraint is part of the code's ON CONFLICT clause. Old code against the new schema fails ingestion outright, and vice versa. The sequence is stop workers → migrate → deploy → start, not deploy.sh's pull-then-migrate order.

10

Next steps

1. Archive before drop — the important one

Retention is live and permanently deletes data at 60 days. There is no archive. Day 61 is simply gone.

The original design called for exporting a partition to Parquet, verifying its row count and checksum, writing a manifest, and only then dropping it. That part was never built. Partitioning makes it straightforward — a partition is already a clean, immutable export unit.

Deadline: the oldest data is 2026-08-05, so the first real drop lands around 5 October 2026. Nothing is at risk before then.

2. Frontend, two small changes

  • Timezone picker can now be refused. PATCH /customers/{code} returns 409 once a tenant has entries. It currently surfaces as a toast containing a long paragraph; it should open the confirm modal with the reason and a "change anyway" action that resends with allow_mixed_timezones=true.
  • Partition health line on the AUTO-POLL card — one line, additive.

Briefed in docs/plan/2026-08-06_frontend-partition-status-line.md. Neither blocks anything.

3. Known issue, deliberately left alone

log_entries.job_id still cascades from jobs, and its index was dropped long ago as unused. A tenant purge already sequential-scanned; after partitioning that becomes roughly 130 sequential scans. Admin-only path, so it is slow rather than broken — and it was left rather than restructuring deletion semantics again.

4. Pre-existing schema drift

alembic check reports the raw pgvector embeddings table, some nullable created_at/updated_at columns, and three log_transactions indexes created by migration b9d4f2a7c318 that were never declared on the model. All of it predates this work.

5. Then the actual goal — machine learning

Transaction failure-risk prediction. log_transactions.status is already a usable label and duration_ms a usable regression target. The data foundation this whole exercise was building is now in place: entries are immutable, transactions are deterministic and idempotent, and history ages out on a predictable schedule.

Root-cause classification is not label-ready — error_text is free text, which is evidence rather than a verified cause. It needs a taxonomy and operator-confirmed resolutions first.
