01

What it does, in one page

A background worker watches the transactions Stage 2 produces, decides which ones a tenant asked to be told about, and sends a card to their Teams channel — durably, paced, and without drowning anyone.

The four guarantees

  • Nothing is lost. The alert is committed to the outbox before any HTTP, so a Teams outage or a restart cannot drop it.
  • Nothing is sent twice. Dedupe by dedup_key, even across replays, rule edits and cursor resets.
  • Nothing is wrong. A transaction that is still changing does not alert, because a false alert here could never be corrected.
  • Nothing floods. Paced per channel, fair across tenants, and collapsed into a summary past a per-rule cap.

What it is not

  • Not a pipeline stage. Stage 1 and Stage 2 do not know it exists and never call it.
  • Not event-driven. It polls Stage 2's output table on its own clock.
  • Not live yet — notifications_enabled is False in production.
02

The shape: four layers, each with one job

The separation is the design. Each layer answers one question, and each mechanism has exactly one home — so a change to pacing cannot affect what alerts, and a change to rules cannot affect how fast anything sends.

Discovery

  • lag stay 60 s behind the present, so late commits are not skipped
  • seal gate skip rows Stage 2 is still rewriting

Transport

  • channel adapter Teams works; Slack and WhatsApp are refused at config time

Why the layering is load-bearing, not tidiness

Originally sending happened inside rule evaluation. That single fact made three separate problems unfixable: there was nowhere to put a rate limit, one tenant's flood blocked every other tenant in the evaluation loop, and a 429 was indistinguishable from a broken channel. Splitting delivery out was the change that made the other five possible.

03

One tick of the worker

Everything runs on one loop, every 10 seconds. The order of the four steps matters and each is commented in the source with why.

# app/services/workers/notification_worker.py
while True:
    await run_rules_once()      # 1. discover + decide → outbox rows
    await rollup.run_once()     # 2. summarise what the burst cap suppressed
    attempted = await deliver_due()   # 3. the ONLY place HTTP happens
    await _report_position()    # 4. tell retention how far we have consumed
    await asyncio.sleep(settings.notification_poll_seconds)
  • Rollup before the drain, so a summary published this tick goes out on the same tick rather than waiting for the next one.
  • Publishing and draining in one tick is why moving the send out of the publish path cost no latency: a fresh delivery has next_attempt_at IS NULL, which the drain already treats as due.
  • Reporting last, after the work it describes, so the published position can never get ahead of what was actually consumed.
  • Every step is failure-isolated. The whole body is wrapped so one bad tick logs and retries rather than killing the loop.

Two lines start all of it

# app/background.py
151    notification_dispatcher.register()                           # wire the subscriber
152    tasks.append(asyncio.create_task(run_notification_worker())) # start the loop

Line 151 is easy to miss and load-bearing: it is the only link between rule evaluation and delivery. The engine publishes to a bus and never imports the dispatcher. Without it, rules evaluate correctly every ten seconds and nothing is ever sent.

04

Discovery — finding what is new

app/services/notifications/cursor.py. A cursor is a bookmark: one timestamp per rule saying “I have read up to here”.

Three mechanisms, three different jobs

MechanismJobIf it were wrong
Cursordo not re-read old rows wasted work — output still correct
Lagdo not read rows still being written a row is missed permanently
Seal gatedo not read rows still changing a false alert that can never be corrected

Why the lag is correctness, not tuning

created_at is stamped when Python builds the row, not when Postgres commits it. A long Stage 2 transaction can therefore commit a row whose timestamp already sits behind a cursor that has moved past it:

10:00:01  Stage 2 builds txn-X, stamps created_at = 10:00:01
10:00:20  notifications reads to 10:00:15, moves cursor → 10:00:15
10:00:30  Stage 2 COMMITS txn-X — created_at still says 10:00:01
          txn-X is behind the cursor. It is never read.

Dedupe cannot rescue this — it prevents duplicates, it cannot recover something never seen. Staying 60 s behind guarantees everything that could write into a range has committed.

Why created_at and not started_at

started_at is when the log line happened; created_at is when the row was written. Backfill a week-old file and those rows have an old started_at but a new created_at. Cursoring on event time would silently skip every backfilled transaction — which is exactly what the old one-hour lookback did.

The seal gate

app/services/notifications/rules/stability.py. Stage 2 rewrites its unsealed tail constantly, so a transaction's status is not final the moment it appears.

incomplete + unsealed  →  wait      # in flight; will probably become success
incomplete + SEALED    →  alert     # past the abandon window — the response is never coming
error / soft / success →  alert     # already terminal

Only incomplete is gated. Requiring a seal for everything would delay a genuine error by up to the 15-minute seal window, which defeats the point of alerting; notification_alert_only_sealed exists for anyone who prefers the accuracy.

The invariant everything rests on

Skipping an unsealed row is only safe because it comes back. Stage 2 does DELETE + INSERT, stamping a fresh created_at, so a gated transaction re-enters the feed the moment it seals. That has its own test — if a rebuild ever preserved created_at, the gate would silently become “never alert” instead of “alert later”.

05

Decision — should this alert?

The three rule types

TypeKindMatches onUses the cursor?
status_matchstreamingstatus list + optional method filteryes
text_matchstreamingsubstring or regex over chosen fieldsyes
digestwindowone summary per intervalno — its own window arithmetic

Only rules with status = active are evaluated. Each rule keeps its own cursor, so activating or replaying one never disturbs another — but a customer's rules are read with a single query starting from the oldest cursor among them, because planning a query against the partitioned table costs ~50 ms regardless of what it returns.

Dedupe, and why it stays

The cursor stops us re-reading; dedupe stops us re-sending. They are not redundant: a rule edited, replayed, or with a reset cursor would re-alert without it. Dedupe is the safety net that makes every other optimisation safe to get wrong.

What dedupe rests on: a transaction id that does not move

A dedup_key is built from the transaction's id, so “nothing is sent twice” is only true while that id is stable. It was not.

Stage 2 deletes and rebuilds every transaction in a re-stitched window, and the id was derived from the transaction's content — the hash of its REQUEST entry, or of its earliest entry when it had none. A backfilled file that adds an earlier line, or supplies the REQUEST line that failed to parse, moved the anchor and therefore the id. Measured on production over one full day: 216 of 16,153 transactions (1.3%) have no REQUEST entry and were exposed to this. The same transaction would alert again under a new identity, and the deep link in the first card would 404.

The fix: identity is carried, not recomputed

app/services/mnp_log_ingestion/pipeline/continuity.py. log_entry_assignment already records which entries belonged to which transaction, and regroup_window was discarding that a moment before it would have answered the question. It now reads {entry_id → transaction_id} in one bulk query before the delete, and each rebuilt group reuses the id of the transaction that owned the plurality of its entries. A merge keeps the larger contributor's id; a split keeps it for the larger half.

New groups still mint uuid5 exactly as before, so no id that exists today was rewritten — deploying it re-fired no alert and broke no saved link. Cost is one added query per rebuild: 0.50 ms, on rows that were about to be deleted anyway.

Nothing in the notification pipeline changed for this. That is the point: dedupe was never the broken part, it was resting on something that was.

The burst cap and the rollup

app/services/notifications/rollup.py. Pacing protects the webhook; this protects the person reading the channel, for whom 500 cards delivered slowly is still 500 cards.

  • Suppressed is recorded, not skipped. Every match keeps its event row and a suppressed delivery row. The cursor has already moved past those transactions, so nothing else would record what the summary covered.
  • Only completed windows are summarised, and idempotently by dedup key — the same rule the digest evaluators follow, so there is one notion of “window” to learn.
  • Summaries are exempt from the cap. They carry their rule's id for provenance, so without the exemption the cap would suppress the very card reporting the suppression and the flood would vanish in silence. Found by a test, not in production.
06

Delivery — the one place HTTP happens

dispatcher.enqueue writes rows and never sends. dispatcher.deliver_due — the outbox drain — is the single seam where anything leaves the system, which is what makes pacing, fairness and Retry-After possible at all.

enqueuepersist event + one delivery row per channel Commits BEFORE anything is sent. This ordering is why a Teams outage or a crash mid-send never loses an alert.
the drain claims what is due
_claim_dueFOR UPDATE SKIP LOCKED, joined to the tenant Deliberately unbounded: fairness must be decided across the whole due set, or a LIMIT would cut the batch before round-robin ever saw the quiet tenants.
fairness
pacing.round_robinone per tenant in turn A flood delays itself rather than everyone. Order within a tenant is preserved, so fairness across tenants does not become unfairness inside one.
budget
_spend_budgetsclaim what fits; reschedule the rest Over budget → rescheduled inside the rate window, jittered. NOT a failure: no attempt consumed, no error recorded.
_attempt_deliveryadapter.send(...) Concurrent across channels — one failing channel never holds up the others.

Three kinds of “it did not go out”, and why they must not be confused

OutcomeAttemptsNextConfusing it with the others would…
Over budgetunchangedinside the rate window, jittered …dead-letter a good alert after 50 quiet deferrals
Throttled (429)unchangedthe server's own Retry-After …burn the retry budget for being told “slower”
Failed+1backoff ladder, dead at 50 …retry forever, or give up on a network blip
Permanently broken+1dead immediately …spend 50 attempts on code that does not exist

Only a missing implementation counts as permanent. A disabled channel deliberately does not — someone can re-enable it, and treating that as fatal would discard alerts an operator was about to rescue.

The budget needs no counter table

Remaining allowance is measured by counting deliveries already made inside the window. That stays correct across restarts and across worker processes for free, and there is no counter to drift out of sync with reality.

08

Multi-tenant: rules and channels

# dispatcher._resolve_channels — read the ORDER
where(customer_code == event.customer_code,   # 1. tenant FIRST
      enabled.is_(True))                      # 2. then enabled
if event.target_channel_ids:                  # 3. only THEN narrow
    rows = [r for r in rows if str(r.id) in wanted]

Because step 3 filters a list that is already tenant-scoped, a rule naming another tenant's channel id gets nothing. Targeting can only narrow, never reach across. Empty targeting means all of that tenant's enabled channels.

Everything that could be a shared resource is per-tenant or per-channel: the rate budget is per channel, the burst cap is per rule, and the drain is fair across tenants. One noisy tenant cannot silence, slow, or starve another.

On the testing

The subsystem had no tests at all before this work. It now has 137, written failing-first. Every correctness decision was mutation-tested — the fix reverted, the suite re-run, and the failure confirmed. Three of those mutations survived and exposed weak tests rather than weak code; two others turned out to be equivalent mutations, which corrected a comment that had overclaimed.

Two bugs caught by tests rather than production

  • advance_rule was async but called without await — so no cursor ever moved. It does no I/O, so it is now synchronous; that shape makes the mistake impossible rather than merely fixed.
  • The rollup summary suppressed itself. It carries its rule's id for provenance, so the burst cap counted it as one more alert from that rule. The entire flood would have vanished in silence — strictly worse than sending all 500 cards.

And one real bug found via a flaky test

A recurring failure in the Stage 1 queue tests turned out not to be a test problem. reset_abandoned_objects set available_at from the app host's clock while claim_one gates on the database's (available_at <= clock_timestamp()). Measured drift here swings +3 ms to −55 ms, so a re-armed queue row was silently unclaimable whenever the host ran ahead. Fixed, and guarded by a test that checks 25 times, since it only shows on the positive excursions.

10

Reusing this for ML and analytics

Notifications is the first incremental reader of log_transactions. The machinery it uses is deliberately generic, so the next one costs almost nothing — and Stage 2 never changes.

But a cursor is not right for every consumer

This is the part that is easy to get wrong. ML training wants a frozen, reproducible range — a moving bookmark would shift the dataset under every run and destroy reproducibility. Analytics computing “yesterday” wants one complete day, not “what is new”.

ConsumerWhat it wantsMechanism
Notificationswhat is new, nowcursor + lag, register in consumer_cursors
ML online featureswhat is new, nowsame — cursor.py is not notification-specific
ML trainingall of March, frozen, re-runnabledate range — no cursor
Analytics rollupyesterday, complete, onceread the day's partition directly

Daily partitioning pays off a second time for the batch readers: SELECT … FROM log_transactions_2026_08_07 is one partition — no scan, no cursor, no coordination.

Adding an incremental consumer, concretely

  1. Read with cursor.window_stmt(...), passing any extra filters your subsystem needs — it takes them rather than knowing them, which is why the seal gate lives in rules/stability.py and not in cursor.py.
  2. Keep your own position however suits you; publish the oldest one you still need via consumer_cursors.report(...).
  3. That is all. Retention picks you up automatically, and Stage 2 is untouched.

12

Caveats and what is not done

  • It is switched off. notifications_enabled=False in production. Nothing here is live yet.
  • Deploying needs a stop. Three migrations (b3d914c7ea52, c7a02f68b1d4, d5c81b60a473) — stop workers, migrate, deploy, start. Not deploy.sh's pull-then-migrate order.
  • The lag delays every alert by up to 60 s. That is the price of never missing a row committed late, and it is not negotiable downward without reintroducing that bug.
  • Seal-gating has a residual edge. A late error entry can still join an already-responded transaction inside the seal window and flip success to error. Rare but real; notification_alert_only_sealed closes it at the cost of delaying every alert.
  • Rollup hides detail by design. The summary must carry enough — count, top offenders, window — that nobody needs the cards it replaced. Suppressed rows remain queryable.
  • A stale consumer stops protecting itself. After 24 h retention proceeds without it, logged CRITICAL. Blocking forever would fill the disk, which is the worse failure.
  • Slack and WhatsApp still do not work. They can no longer be configured, and /channel-types still lists them separately so a picker can grey them out rather than hide the roadmap.
  • The event bus earns nothing today. It loops over subscribers and there is exactly one. Indirection with a single implementation — worth keeping only if a second subscriber is genuinely coming.
  • Three complexity hotspots remain, all untested: publish_manual_endpoint (CRAP 16), _validate_rule (7), and TeamsChannel._facts (9). Not touched by this work — refactoring untested code blind would risk changing behaviour with nothing to catch it. Tests first, then decompose.
