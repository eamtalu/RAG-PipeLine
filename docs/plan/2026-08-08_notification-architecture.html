01

Where notifications sit: outside the pipeline, not inside it

Stage 1 and Stage 2 are joined by queues — a producer commits a ticket, a consumer claims it. Notifications is the one component that does not work that way. It polls Stage 2's output table on its own clock.

Why this matters

Because nothing tells it when there is new work, it has to guess — "look at the last hour, every ten seconds." That guess is the origin of three separate flaws in section 4: wasted scanning, missed backfills, and a hard cap that silently truncates.

02

Entry points and the call chain

Two lines at startup. The first is easy to overlook and is what makes the whole thing work.

# app/background.py
151    notification_dispatcher.register()                           # wire the subscriber
152    tasks.append(asyncio.create_task(run_notification_worker())) # start the loop

register() is the only link between rule evaluation and delivery — it calls bus.subscribe(handle). The engine never imports the dispatcher. Without line 151, rules would evaluate every 10 seconds and nothing would ever be sent.

Six nested loops multiply

tenants × transactions × rules  →  events × channels  =  HTTP calls

At the measured production rate, one broad rule and one channel: 1 tenant × 567 transactions × 1 rule = 567 events × 1 channel = 567 POSTs. Add a second channel to that tenant and it is 1,134 — from the same 567 matches.

03

How it works today

Four tables, two of them per tenant

Tenant isolation is already correct — read the order

# app/services/notifications/dispatcher.py:110-118
stmt = select(CustomerNotificationChannel).where(
    CustomerNotificationChannel.customer_code == event.customer_code,  # 1. tenant FIRST
    CustomerNotificationChannel.enabled.is_(True),                     # 2. then enabled
)
rows = list((await db.execute(stmt)).scalars().all())
if event.target_channel_ids:                          # 3. only THEN narrow
    wanted = {str(c) for c in event.target_channel_ids}
    rows = [r for r in rows if str(r.id) in wanted]
return rows

Because step 3 filters a list that is already tenant-scoped, a rule naming another tenant's channel id gets nothing. Targeting can only narrow, never reach across. This is worth preserving exactly as-is.

What is already right

  • Unlimited rules and channels per tenant
  • Per-rule channel targeting
  • Tenant isolation, as above
  • Durable outbox — committed before any HTTP
  • Dedupe, backoff, dead-letter after 50 attempts

Rule types

  • status_match — streaming; status list, optional method filter
  • text_match — streaming; substring or regex over chosen fields
  • digest — window; one summary per interval

Only rules with status = active are evaluated.

The flaws

Each paired with the code that causes it. Figures measured on production, 7 August.

#FlawCauseConsequence
1No throttling engine.py:79-82 bare publish loop; dispatcher.py:105 sends at once 500 matches = 500 back-to-back POSTs. A 429 is a generic failure; Retry-After never read
2Send happens inside evaluation dispatcher.py:105 The root cause. No pacing point exists, and one tenant's flood blocks every other tenant
3Full rescan every tick engine.py:61 — started_at >= now() - 1 hour ~567 rows re-read and re-evaluated ~8,600×/day to find a handful that are new
4Unsealed rows are evaluated no sealed filter anywhere in the engine An incomplete transaction alerts, then becomes success — and the stable dedup key means no correction is ever sent. 81 of 412 currently unsealed
5Data can be missed the 1 h lookback and _CANDIDATE_LIMIT = 2000 A backfill of week-old logs is invisible — started_at is old even though the row is new
6Slack/WhatsApp are stubs send() raises NotImplementedError Flows into the normal failure path: fails 50 times, then dead-letters
7One flag-flip from a flood an inactive rule on tmp-live matches error + soft + success — every transaction — pointed at an enabled channel Worker is currently OFF. Turn it on and activate that rule: ~567 messages/hour

The one to understand: dedupe does not prevent work

It is easy to assume dedupe stops re-processing. It does not — look at where it sits in the chain. engine.py:78 runs after the rows were loaded and after every rule was evaluated against them. It only stops the send.

05

The proposal: three layers, each with one job

The current design has no seams — finding work, deciding to alert, and sending are tangled together in one call path. Separating them is what makes every individual fix possible.

Discovery
how do I find work?
  • cursor new where I stopped reading — replaces the hourly rescan
  • lag new stay ~60s behind the present, so late commits are not skipped
  • seal filter new skip rows still being rewritten
↓ candidate transactions
Decision
should this alert?
  • seal-gating new hold incomplete until sealed; alert other statuses at once
  • dedupe exists unchanged — still the safety net
  • rollup new after N cards from one rule, send one summary instead
↓ rows in the outbox
Delivery
how do I get it out?
  • pacing new token bucket per channel
  • fairness new round-robin across tenants
  • Retry-After new obey a 429 instead of guessing
  • retry / dead exists backoff ladder, give up at 50
↓
Transport
the actual HTTP
  • channel adapter Teams today; Slack and WhatsApp are stubs

The load-bearing change is flaw 2

Everything else depends on it. While dispatcher.py:105 sends during evaluation there is nowhere to put a rate limit, and no way to be fair across tenants. Move sending into the worker that already drains the outbox, and the outbox becomes the single place where pacing, fairness and back-pressure all naturally live.

Deliberately rejected: having Stage 2 write a notification ticket

It looks tempting — it matches the two existing queues. But it reintroduces exactly the coupling that was removed from Stage 2 when three call sites each had to remember to trigger stitching. Stage 2 would have to know notifications exist; then ML; then analytics. The producer accumulates knowledge of every consumer, and adding a reader means modifying the most correctness-critical writer you have.

06

Cursors, plainly

A cursor is a bookmark: one value remembering where you stopped reading. That is genuinely all it is. Nothing is copied anywhere — log_transactions itself is the feed.

Today versus proposed

Today

WHERE started_at >= now() - 1 hour

Returns A, B, C, D, E every tick for as long as they stay inside the hour. Dedupe then discards the ones already sent — after loading and evaluating all of them.

Proposed

WHERE created_at >  :cursor
  AND created_at <= now() - 60s

Returns only what is new. When nothing has happened it returns zero rows and costs almost nothing.

Why created_at and not started_at

started_at is when the log line happened. created_at (log_transaction.py:132) is when the row was written. Backfill a week-old file and those rows have an old started_at but a created_at of now — a cursor on started_at would silently skip them, which is flaw 5 all over again.

created_at is currently unindexed. That index is the first thing to build.

Why the lag is mandatory, not an optimisation

created_at is stamped when Python builds the row, not when the database commits it. A long Stage 2 transaction can therefore commit a row whose timestamp is already behind a cursor that has since moved past it:

10:00:01  Stage 2 builds txn-X, stamps created_at = 10:00:01
10:00:20  notifications reads to 10:00:15, moves cursor → 10:00:15
10:00:30  Stage 2 COMMITS txn-X — created_at still says 10:00:01

          txn-X is now behind the cursor. It is never read.

Dedupe cannot save you here — it prevents duplicates, it cannot recover something never seen. Staying ~60s behind the present guarantees every transaction that could write into a timestamp range has already committed. The lag just has to exceed the longest Stage 2 transaction.

Three mechanisms, three different jobs

MechanismJobIf it fails
Cursordo not re-read old rowswasted work — output still correct
Lagdo not read rows still being writtena row is missed permanently
Dedupedo not send twiceduplicate alerts

The cursor is a performance mechanism. The lag is a correctness mechanism. Dedupe is the safety net. Keep all three — losing the cursor costs speed, losing dedupe costs spam, losing the lag costs an alert.

07

Reusing the pattern: ML and analytics

Every consumer keeps its own bookmark on the same table. No copies, no channel, and Stage 2 never learns any of them exist.

But not every consumer wants a cursor

This is the part that is easy to get wrong. A cursor suits incremental readers. ML training wants a frozen, reproducible dataset — a moving bookmark would shift the data under every training run and destroy reproducibility. Analytics computing "yesterday" wants one complete day, not "what is new".

ConsumerWhat it actually wantsRight mechanism
Notificationswhat is new, right now cursor + lag
ML trainingall of March, frozen, re-runnable date range — no cursor
ML online featureswhat is new, right now cursor + lag
Analytics rollupyesterday, complete, once read the day's partition directly

And this is where daily partitioning pays off a second time. Analytics reads one partition — no scan, no cursor, no coordination:

SELECT status, count(*) FROM log_transactions_2026_08_07 GROUP BY 1;

The cross-consumer concern: retention will delete data out from under a slow reader

The partition worker drops days past 60. It already refuses to drop a day with unstitched windows — days_blocked_by_pending(), gate 2. A slow consumer needs the same protection, or retention silently destroys data it has not read yet.

blocked = await days_blocked_by_pending(db, days) \
        | await days_blocked_by_consumers(db, days)   # min(cursor) across consumers

This is the strongest argument for one shared cursor registry rather than each subsystem hiding its bookmark in its own table: you cannot gate retention on something you cannot see, and you cannot answer "is anything behind?" without one place to ask.

08

Caveats

  • The lag is not optional. Without it a cursor silently drops rows committed by long transactions. It must exceed the longest Stage 2 transaction; measure it, do not guess.
  • created_at resets on every regroup. derive_transactions.py:600 builds a fresh LogTransaction each rebuild, and Stage 2 rewrites the unsealed tail constantly — so the same transaction re-enters the feed repeatedly for ~15 minutes. That is correct (the row genuinely changed) but it means every consumer must be idempotent. Seal-gating removes most of this churn.
  • Seal-gating trades latency for accuracy. Only incomplete is gated by default. The residual edge: a late error entry can join an already-responded transaction inside the seal window and flip success to error — rare, but real. notification_alert_only_sealed=true closes it by requiring a seal for every status, at the cost of delaying every alert by up to 15 minutes.
  • Moving the send off the publish path adds latency. An alert waits for the delivery tick instead of going out during evaluation. Run the delivery loop faster than evaluation (~1–2 s) so worst-case latency stays roughly where it is today.
  • Rollup hides detail by design. The summary card must carry enough — count, top offenders, time range, and a link — that nobody needs the 473 individual cards it replaced.
  • Slack and WhatsApp still do not work. Until implemented, the API should refuse to create channels of those types rather than letting them fail 50 times and dead-letter.
  • The event bus earns nothing today. bus.py:35 loops over subscribers and there is exactly one. It is indirection with a single implementation — worth keeping only if a second subscriber is genuinely coming.
  • Do not add a storage abstraction yet. The argument for one is "storage might move." It has not, and an interface with one implementation is a cost with no benefit — the same trap as the bus. Add it the day a second storage shape is real.

Build order

Sequenced so each step is independently shippable and testable.

#StepWhy here
1Index log_transactions.created_at done Migration b3d914c7ea52. PostgreSQL refuses CREATE INDEX CONCURRENTLY on a partitioned parent, so it is built per partition and attached to an ON ONLY parent index. New partitions inherit it automatically
2Cursor + lag on the engine query done Migrations c7a02f68b1d4 + app/services/notifications/cursor.py. Measured: 50 matching rows publish once on tick 1 (131 ms), then ticks 2-3 read zero rows in 13 ms. Dedupe kept as the safety net
3Seal-gate incomplete done Kills flaw 4. rules/stability.py — applied in SQL, so churning in-flight rows are never fetched. Verified end to end: in-flight incomplete held back, sealed incomplete alerts, unsealed error/success alert immediately
4Move the send out of the publish path The structural change. Nothing in 5 or 6 is possible before it
5Per-channel pacing, fairness, Retry-After Kills flaws 1 and 2 and the cross-tenant starvation
6Rollup threshold + summary card Kills flaw 7 — protects the reader, not just the webhook
7Reject unimplemented channel types at config time Kills flaw 6. Small and independent
8consumer_cursors registry + retention gate Do it before a slow consumer exists, so it is never a retrofit

Steps 1-2 shipped, 8 August

29 tests in tests/test_notification_cursor_chunk28.py — the first tests this subsystem has ever had. All eight correctness decisions mutation-checked; two initially escaped and needed better tests (an exclusive lower bound, and a rule re-evaluating rows behind its own cursor). Everything A-grade complexity. Full suite 378 green.

Two bugs were caught during implementation rather than in production: advance_rule was async but called without await, so no cursor ever moved — it is now synchronous, since it performs no I/O and that shape makes the mistake impossible. And the end-to-end test initially published into a void because bus.publish has no subscribers until dispatcher.register() runs.

One design decision changed after measurement: rules were going to get one query each, but planning a query against the partitioned table costs ~50 ms regardless of how little it returns, so a customer's rules now share ONE query starting from the oldest cursor among them and filter in memory. Query count is unchanged from before; every rule still keeps an independent cursor.
