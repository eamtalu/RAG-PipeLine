The central correctness trap

log_transactions is deleted and rebuilt when late data arrives. Treating every rebuilt row as new and adding its quantity again would silently inflate totals.

02 · Business definition

Consumption is successful physical picking, not every stock-related number

The initial metric uses two independent identifiers and a success gate. Quantity is parsed as an exact decimal from attributes.QuantityPicked.

Included in consumption

  • transaction_type = '002001'
  • method = 'ConfirmPickLine'
  • status = 'success'
  • Populated item number
  • Valid non-negative decimal QuantityPicked

Kept separate

  • Failed or incomplete pick attempts
  • Stock moves and reallocations
  • Receipts, including rejected quantity
  • Stock counts and adjustments
  • Placeholder transaction codes

What the number can honestly claim

It is exact aggregation over captured successful pick transactions. It is not yet an audited warehouse-wide inventory-depletion or financial-consumption ledger.

04 · Correctness under failure

At-least-once delivery with exactly-once effect

The worker does not trust that a row is new. It stores the last version of each contribution and applies only the accounting difference.

aggregate delta = new contribution − old contribution

Before commit

A crash changes neither aggregate nor ticket. The same window remains ready for retry.

→

After commit

The ticket is consumed with the aggregate update. An uncertain replay sees the same version and applies delta zero.

Quantity corrected

Old quantity is subtracted and the new quantity is added.

Net effect: exact difference

Item corrected

The old item's total decreases and the new item's total increases.

Net effect: both items repaired

Success becomes error

The prior successful contribution is removed completely.

Net effect: full retraction

Transaction disappears

Window reconciliation finds the stored contribution missing from the current source.

Net effect: stale value removed

Dirty window repeats

The same version hash produces no accounting change.

Net effect: idempotent replay

Two workers start

A tenant advisory lock allows only one worker to fold that tenant at a time.

Net effect: serialized tenant state

Why this remains explainable

Every item total can be reconstructed from its contribution rows. The aggregate is a performance structure, while the contribution ledger is the audit trail.

05 · Data quality

Bad data is visible, never silently turned into zero

Each candidate becomes a valid contribution, a valid zero contribution, or a named quality issue. The API returns the quality and freshness state beside every metric.

Strong fields

Successful pick method, code, item, decimal picked quantity, event time, tenant, warehouse, user, device, order, and lot.

Use now

Misleading fields

Write timestamp, mutable transaction content, request ID uniqueness, placeholder codes, receipt quantity, and count-field names.

Guard explicitly

Missing business facts

Canonical UOM, cost, authoritative stock balance, complete demand lifecycle, supplier milestones, and reversal semantics.

07 · Scale and technology choice

Materialize once, read cheaply many times

The current direct dashboard queries scan partitioned history and cast JSON for every request. The proposed read path touches only compact aggregate rows.

Time seriesAggregate raw rows across partitionsRead pre-aggregated item-hour buckets
CorrectionWould require full recompute or risk double countSubtract old contribution and add new one

No Flink yet

The measured peak of 13 picks per minute does not justify a separate distributed stateful-processing cluster.

No Kafka yet

PostgreSQL already owns the atomic source-change and durable-work transaction boundary.

No WebSocket first

Two-second revision polling is authoritative, cross-process safe, and meets the selected freshness target.

08 · Delivery roadmap

Prove semantics and correctness before building the dashboard

The sequence places the most dangerous plausible-wrong-total failures ahead of UI work.

Semantic contract and E2E fixture

Confirm known successful, zero, short, failed, incomplete, late, and rebuilt transactions through the end-user path.

Exit: signed-off fixture totals and a failing E2E test.

Schema, models, migration, and ER diagram

Add dirty windows, contributions, totals, hourly buckets, quality issues, and tenant state.

Exit: constraints and Mermaid diagrams validate.

Transactional dirty-window publication

Cover live-tail regroup and historical window repair with an atomic ticket.

Exit: every committed projection change has durable work.

Normalizer, delta fold, and worker

Implement strict parsing, quality quarantine, old-to-new diff, retry, and tenant serialization.

Exit: replay, correction, deletion, and crash tests reconcile exactly.

Backfill and reconciliation

Run bounded tracked jobs and compare materialized totals with a full source recomputation.

Exit: all production differences are zero or explicitly quarantined.

Bounded read APIs

Add status, item list, detail, time series, quality, keyset pagination, and ETags.

Exit: tenant-safe measured index-backed query plans.

Next.js analytics experience

Add revision polling, stale-state preservation, race prevention, tenant switching, accessibility, and responsive visual review.

Exit: a correct total is visible within 5 seconds and never appears fresh when stale.

Controlled production rollout

Deploy schema, backfill, enable one tenant, reconcile continuously, then expose the UI behind a feature flag.

Exit: freshness, correctness, database load, and web health remain within thresholds.

Definition of done

Replays and rebuilds have exactly-once effect, corrections retract old values, full recomputation matches, invalid data is visible, queries are bounded, and the browser shows both the number and whether it can be trusted.
