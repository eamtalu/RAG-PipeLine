eSmart Eye · architecture, approved 9 November 2026

eSmart Agent: one shared runtime, many tenants, many sources

A framework for the agent side of eSmart Eye: a stateless runtime that every tenant shares, typed tools over a single query model, a model router that pins a provider per run, explicit-only memory, and the controls that let hundreds of people use it at once without reading each other's data. Nothing here is built yet; this is the design the roadmap implements.

One request

What happens to a question, in order

1
channel

A Teams question arrives on SQS, or a web question on HTTP

The adapter builds AgentRequest{request_id, tenant, principal, profile, text, conversation_id, conversation_type, action?, deadline}.

2
gateway

Authenticate, resolve the tenant from the credential, build the Principal

For SQS: re-resolve customer from the Entra tenant id in the backend's own binding table; refuse a mismatch. Object id required.

3
gateway

Admission and idempotency

Per-tenant and per-user counters. Claim agent_runs(tenant, request_id): running → leave it; done → re-post the stored result; new → proceed.

4
runtime

Load the profile, assemble context

History from the store; explicit preferences only in personal conversations; a catalogue excerpt (60 s cache). Provider pinned by the router.

5
runtime

Guards before, then the tool loop under budgets

Manipulation and topic checks. Loop until answer or budget: iterations, tokens, two tool failures, wall clock shorter than the queue's visibility window.

6
capabilities

Each tool call runs a DataQuery through a connector

Allow-listed, parameterised, timed out, breakered; results in a capped envelope; free text sets the untrusted flag, after which no side effect runs without confirmation.

7
runtime

Guards after, then presentation over the trace

Evidence, blocks, citations; grounding (every figure in the answer or a chart came from a tool result); redaction; URL and phone stripping.

8
gatewaychannel

Persist and deliver

Redacted trace, turns, usage, audit row; run marked done with the stored result; the channel posts it (the edge's /internal/answers, or the HTTP reply).

Query model

One data language, many executors

Boundary. The Universal Query Model provides a common contract for structured, read-oriented data retrieval across compatible sources. Each connector translates this contract into its native query mechanism. It is not intended to represent every possible API operation or business action. Sources requiring domain-specific operations expose typed business tools through the same Tool Registry and execution framework.

Within that boundary, tools, evidence, grounding and charts are written once against DataResult. The source field is not free text: the registry generates it into the tool schema per request as the tenant's enabled query instances, and the executor checks it again against the execution context. Tenant identity never comes from a model argument.

             entity, measures: [{field, agg}], filters: [{field, op, value}],
             group_by: [field | {field, bucket: hour|day|week|month}],
             sort, limit, window: {start, end} }

Capabilities in detail

How data sources are managed: kinds are code, instances are configuration

A connector kind is a package, one per source type, shipped with the product. A connector instance is one row per tenant per source, created by an admin without a deploy. The registry builds the offered tool set from the tenant's enabled, healthy instances on every request.

Adding a source (admin, no deploy)
1. POST /tenants/{t}/connectors with kind and credentials.
2. The secrets store encrypts the credential; the row is testing.
3. The test action runs health.py and catalogue.py introspection.
4. The admin prunes the allow-list (tables, columns, endpoints); status enabled.
Using a source (every run)
1. The gateway loads the tenant's enabled instances.
2. The registry builds the offered set and generates each tool's description from that instance's catalogue.
3. The model calls sql:wms.query(DataQuery).
4. The executor compiles it: parameterised, allow-listed, timed out, capped, breakered per instance.
5. The DataResult enters the trace; renderers read it.
Removing or breaking a source
Disabling the row, a failed health check or a rotated credential drops the instance from the offered set on the next request. Nothing restarts; the model simply stops seeing the tool, and the catalogue cache expires within a minute.

Model router

Profiles state needs; the router picks and pins a provider

ModelPolicy {primary, fallbacks[], cheap, embeddings}   per profile, overridable per tenant
  │
  ├─ capability match      needs tool calling? context size? → ineligible providers drop out
  ├─ breaker closed?       open after N failures in M s; half-open probes
  ├─ bulkhead has a slot?  max in-flight per provider
  ├─ budget ok?            per-tenant tokens and cost for the day
  └─ pin for this run    mid-run failure → rerun the whole run once on the next fallback

providers: Bedrock eu-west-2 (Qwen, Claude) · Anthropic · Ollama on-prem · OpenAI (embeddings)
per call:  timeout · retry with jitter on throttling only · tokens in/out/cached · cost · latency
caches:    catalogue per tenant (60 s) · tool results per tenant+args (30-60 s) · no answer cache
capacity:  default Bedrock quotas + p95 60 s assumed → ~10-20 concurrent runs; quota increase in stage 2
Memory

Explicit only in v1

Conversation
Last N turns per conversation id, plus the user in group chats. 30 days. Replayed with tables stripped, as today.
User preferences
Keyed by (customer, Entra object id). Enum keys only: units, home site, default window, chart preference. Written by a preferences.set tool after the page confirms. Read only in personal conversations. Listed and clearable from the tab. Tenant toggle, off by default.
Tenant knowledge
Glossary, site names, shift times. Written by admins only; the model never writes it.
Not in v1
Inferred preferences, topic profiles, episodic summaries. They are behavioural profiles of employees and need a lawful basis, a notice and a tenant switch first.
Tenancy and scale

Shared harness, per-tenant everything else

One runtime for all
Stateless workers; TenantContext and Principal built once per request and passed explicitly. No globals read inside a run.
Fairness at admission
Per-tenant and per-user limits at the edge (before enqueue) and the gateway. Workers use a plain semaphore; SQS messages are never bounced for fairness.
Hundreds of users
Is a few dozen questions in flight. Horizontal consumer processes; the ceiling is the provider quota, so the capacity table decides when to raise it.
Database discipline
No session across model calls; explicit statement timeouts; row-level security with SET LOCAL app.tenant on agent-store tables as a backstop.
Caches keyed by tenant
(tenant, profile version, catalogue hash, args). Never an answer cache.
Later, on request
Dedicated worker pools per tenant, data-region routing, per-tenant dashboards. Same code, different process set.
Execution context and storage

One shared runtime, many isolated execution contexts, separately scoped memory

gateway:  authenticate → tenant → principal → admission (atomic, shared store) → claim run row
          → ExecutionContext(frozen)            built once, here, nowhere else
runtime:  run(ctx)                               ctx is the first argument everywhere
          router.choose(ctx.model_policy, ctx.budget)
          memory.load(ctx.tenant_id, ctx.user_id, ctx.conversation_id)
          registry.for_context(ctx)              tools bound to ctx at build time
          policy.may_run(ctx.principal, tool)
          observability.bind(ctx.request_id, ctx.trace_id)
tools:    executor.run(ctx, DataQuery)           the model supplies DataQuery only; never the tenant
Immutable after the gateway
A frozen object: request id, trace id, tenant, principal, profile, conversation, preferences, deadline. No model output or connector result has a path to it.
No shared mutable state
Each run owns its context and trace; the graph is built per run; process-wide objects are stateless clients, pools and tenant-keyed caches with immutable values. A layout test forbids other module-level mutables.
Quotas are shared and atomic
Counters live in quota_windows and change by one INSERT … ON CONFLICT … RETURNING; the edge uses its DynamoDB ADD. Five workers see one number. In-flight counts are swept by deadline.
Memory across channels
Preferences by tenant + user: set in Teams, applies on the web. History by conversation: Teams and web never mix. Two runs at once both append; preferences last-write-wins.

Repositories take the context, not raw ids, so a query cannot be written with the user and without the tenant. Row-level security on every table, with the transaction setting app.tenant_id from the context, makes a forgotten filter return nothing rather than everything.

What exists today

The design builds on a real codebase; these are the gaps it closes

Keep
LangChain tool loop, guards (manipulation, topic, grounding, secret redaction), evidence from the trace, SQS consumer with heartbeat, tenant-scoped analytics reads, conversation turns, customer registry.
Fix first (stage 0)
No API authentication; consumer trusts the message's customer; no run deadline; one DB session held across model calls on a 5+10 pool; no idempotency; per-tenant-only rate limit; secrets in plain JSONB; no request ids or JSON logs.
Rework
Three agent subclasses → profiles; tools over a single query model; pgvector table without a tenant column and a broken search path; free-text actor on actions; client-supplied history on the web route.

Decisions

Settled on 9 November

1 · Shared runtime
Per-tenant policy; dedicated pools later and on request.
2 · Analytics is the record
History lives there; connectors are for live state.
3 · No free-form SQL or code
Catalogue-bounded query builders only.
4 · Router owns the provider
Profiles name needs; pinned per run.
5 · Memory explicit-first
Personal conversations only, enum keys, confirmed, clearable, off by default per tenant.
6 · Stage 0 before any source
Authentication and secrets come first.
7 · Stay one repo for now
Agent is a package with a layout test; extraction when a second consumer exists.
8 · One query model
DataQuery for every source; renderers written once; analytics implements it first.
9 · Identity
Entra object id plus a backend roles table; group-claim sync later.
10 · Capacity
Default Bedrock quotas and a 60 s p95 assumed until measured.
